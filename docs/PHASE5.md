## 1. Goal and scope

Today a backup happens when a person asks for it. Phase 5 makes it happen **by itself**, keeps the storage from growing without end, and makes it safe to keep the archives somewhere other people can reach: **one cron job** calls ThreadSafe every few minutes and the schedule of every site, kept in its profile, decides what is due; **retention** removes the backups that are not wanted any more; **encryption** makes an archive unreadable without a key that the server does not hold.

| In scope | Out of scope (later) |
|---|---|
| schedule per profile (cron expression, a time zone for all), the trigger `threadsafe cron` (command line) and a protected address for hosts without a command line cron, a heartbeat the dashboard watches, a queue (one backup at a time), missed runs made up once, failed runs retried a few times, interrupted runs continued | a graphical cron editor beyond a text field with a preview of the next runs; several schedules per profile; schedules of other kinds of job (checks, mails) |
| retention per profile: keep the last *n*, delete older than *d* days, stay under a size; the newest good backup is never deleted; a backup can be pinned; a dry run and a preview | grandfather-father-son schemes; retention across profiles; retention on remote storage |
| archive encryption in the format of `age` with public keys (the key pair of the owner) and an optional passphrase; keys made by a command; encrypted archives that can be checked (as far as the key is not needed), downloaded, restored by the command and by `restore.php` | encrypting the files of a site at rest, encrypting profiles or the data directory, key escrow, hardware keys |
| the changes of the command line, the profile page, the dashboard (next run, heartbeat) and the System page that these need | **remote storage** (SFTP, S3, WebDAV; `Postproc` stays as it is), notifications by mail, a second administrator |

Phase 5 ends with the **proof on the Docker stack**: a backup that the trigger starts at the scheduled time (command line and address, under the limits of 5 seconds and 64 MB), retention applied to real backups, an encrypted backup that the standard tool `age` can open, and that same backup restored by `threadsafe restore` and by `restore.php` through the wizard.

## 3. Design

### 3.1 What changes in the data

- **`SiteProfile`** gets three optional fields (a profile without them is what it is today):

```json
{
  "schedule":   {"cron": "30 3 * * *"},
  "retention":  {"keep": 14, "maxAgeDays": 90, "maxBytes": 21474836480},
  "encryption": {"recipients": ["age1ql3z7hjy54pw3hyww5ayyfg7zqgvc7w3j2elw8zmrj2kg5sfn9aqmcac8p"]}
}
```

  Every key inside is optional; `null` or absent means "no such rule". Editing them is `profile edit --schedule=... --keep=... --recipient=...` and the profile form.
- **`config.json`** gets `schedule.timezone` (an identifier such as `Europe/Berlin`; default: the time zone of PHP, which is UTC where nobody set one), `schedule.expectedIntervalMinutes` (how often the trigger is meant to come; default 15; the heartbeat warning is derived from it), `schedule.graceMinutes` (how late a scheduled run may still be made up; default 360), `cron.secret` (the secret of the address; empty = the address does not exist), `cron.mode` (`auto`, `worker` or `ticks`, see 3.3).
- **State of the scheduler:** `data/schedule/<profile>.json` (the last instant that was handled, the number of attempts, the time of the next retry) and `data/heartbeat.json` (time, how it was called, what it did). Both are caches in the sense of the rule "the file system is the source of truth": lose them and the worst case is one extra or one skipped run, and the backups on disk show what exists.
- **Backups and sidecar:** the sidecar file gets `encryption` (`{"format": "age", "recipients": 2, "passphrase": true}`), the entry `pinned` (a backup that retention must not delete) and `source` (`manual`, `schedule`). Older files read as before.

### 3.2 The schedule

- **Cron expressions** are the five fields of the classic `crontab` (minute, hour, day of month, month, day of week) with `*`, lists, ranges, steps, names of months and days, and the shortcuts `@hourly`, `@daily`, `@weekly`, `@monthly`. When both day fields are restricted either may match (the rule of Vixie cron). `CronExpression::next(DateTimeImmutable $after)` returns the next instant in the configured time zone and `previous()` the last one before now; both are pure functions of the expression, the instant and the time zone.
- **Daylight saving time:** an instant that does not exist (02:30 on the day the clock jumps forward) is run at the first instant after the gap; an instant that exists twice (the hour when the clock goes back) runs once, at its first occurrence. **The rule is ours, not PHP's** (spike 1b): `DateTimeImmutable` resolves a repeated hour differently per zone (the second occurrence in Berlin, the first in New York) and moves a time inside a gap by an hour, so `CronExpression` builds each candidate from its wall-clock parts and decides explicitly (the smallest valid instant; in a gap, the transition instant). It also does not use `ext-calendar` (`cal_days_in_month`), which is not installed everywhere. A test table pins both cases for several zones.
- **When is a profile due?** The scheduler takes the **latest scheduled instant `t` that is not after now**. The profile is due if `t` has not been handled (state file) and now is at most `graceMinutes` after `t`; handling means "a backup with this `t` was started, or `t` was skipped on purpose". A `t` older than the grace is **skipped** (audit entry `schedule.skipped`) and the next one waits. So after the server was off for a day exactly one run is made up if it is still within the grace, and never a pile of them.
- **A schedule counts from the moment it is set** (`since` in the state file): setting or changing it, in the command or in the browser, resets the state to "now", so that a profile that gets the schedule `0 3 * * *` at 05:00 does not start a backup at once because 03:00 lies within the grace. A profile that has a schedule but no state file (it was lost, or the profile was copied in) is treated the same way at the first call of the trigger: the worst case is one run skipped, never one nobody asked for.
- **A run that fails** is tried again after 15 minutes, twice at most, as long as the grace holds; then it is given up (audit entry, dashboard warning). A run that is stopped by the trigger being absent is not a failure: it is *interrupted* and continued (3.3).
- **The rhythm of the trigger:** the scheduler only looks at the moment of a call. A trigger that comes once a day (the customer host) makes a run happen when the call comes within the grace after a scheduled instant; the time of the host's cron must therefore lie shortly after the schedule's time, and a schedule more frequent than `schedule.expectedIntervalMinutes` is warned about (section 8, finding 10).
- **The queue:** only one backup runs at a time in the whole installation (the rule of [PHASE4.md](PHASE4.md) 3.4). Profiles that are due wait, ordered by their scheduled instant. A manual backup counts: if one is going, the due ones wait for it.

### 3.3 The trigger

One cron job (or one call of a monitoring service) is all the host needs. It does two things.

**`php bin/threadsafe cron`** (command line, preferred): a **CLI task**. No PHP time limit, due backups run in the calling process, the database is read in one consistent snapshot. In order: write the heartbeat; take the instance lock `locks/cron.lock` without waiting (if another trigger is working, end quietly with exit code 0); continue a run that was interrupted (a run whose lock is free and that is not a recently ticked web run); then, for each due profile in the order of the queue, start a scheduled backup and run it to its end, apply retention, go on to the next; end. If a host kills the process (some hosts cut cron jobs after minutes), the next call finds the run interrupted and continues it, and the manifest then says `consistency: table`.
  Output is one line per action, so that a mail from cron says something useful; `--quiet` prints only problems; the exit code is 0 when nothing went wrong, 2 when something was refused, 3 when a backup failed.

**`GET /cron/<secret>`** (a protected address, for hosts whose cron can only fetch a URL, `wget -q -O - ...` or `curl -s ...`, and maybe only once a day, as on the live host). Each call writes the heartbeat and then works in one of two modes (`cron.mode` in the settings: `auto`, the default, `worker` or `ticks`):
  - **Worker mode** (`auto` when a process can be started: `exec` or `proc_open` is available and `PhpBinary` finds a PHP). If something is due or interrupted and no worker is alive (`locks/cron.lock` is free), the call starts `threadsafe cron` as a **detached process** and answers at once. The process is the CLI task above: no time limit of the request, snapshot consistency. Spike 1c showed on the live host that such a process lives on after the request has ended. The rules of how it is started come from that spike (section 8, findings 8 and 9): the PHP binary that `PhpBinary` names, **a clean environment** (`env -i PATH=...`; a child that inherits `REQUEST_METHOD` or `QUERY_STRING` is run by the CGI binary as another request, which started itself over and over in the spike), standard input `/dev/null`, output to a file under `data/`, `setsid` where it exists, and never a second worker while the lock is held. One call a day is then enough for a daily schedule.
  - **Tick mode** (`auto` when no process can be started, or `ticks`): a **web task**. The call does **one tick** of work under the limits of the request: it continues the run that is going or interrupted, or, if a profile is due, starts a run and does its first tick; with a call every minute (from the host's cron or from another server) a backup goes on by itself. The database is then read table by table (`consistency: table`).
  - The answer is a few lines of plain text; its first word is `idle` (nothing to do), `started` (a worker was started), or `working` (a worker is alive, or a tick was done and more is due), so that a script on another server can call again at once while the answer says `working`. A call that finds nothing to do must be cheap (spike 1d): it reads the profiles and only the **file names** of each storage (the instant of a backup is in its name), not the sidecars; it takes well under 100 ms for 50 profiles with 100 backups each, so no index of the scheduler's own is needed.
  - The address exists only if `cron.secret` is set (`threadsafe admin cron-secret` makes a long random one, 32 bytes, and prints the line for the crontab). It exists **independently of `web.enabled`**: the interface can be switched off (every other address is "not found") and the trigger still works; without a secret nothing is there at all. The secret is compared in constant time, wrong ones are slowed down by the same `Throttle` as the login, and the answer to a wrong one is the same plain "not found".
  - A secret in an address ends up in the access log of the web server and in the history of whoever types it. Say so in the documentation; the secret gives the right to start backups and nothing else, and it can be replaced with one command.

**The heartbeat** is written on every call: the time, `cli` or `web`, what was done. The dashboard shows "last trigger: 4 minutes ago" and **warns when it stays away** for longer than `max(2 × expectedIntervalMinutes, 30)` minutes while at least one profile has a schedule; the System page says how to set the trigger up (the exact `crontab` line with the real paths, the exact address). A profile that has a schedule and no heartbeat ever shows "no trigger has called yet".

### 3.4 Retention

- **Rules** (all optional, any combination): `keep` - at most this many backups are kept; `maxAgeDays` - older ones are removed; `maxBytes` - the oldest ones are removed until the total is under the limit. Only **complete, usable** backups count (status `ok`, `ok-with-warnings`, `unverified`).
- **Never deleted:** the newest usable backup (so a failing schedule or a mis-set rule cannot leave the site without a backup); a **pinned** backup (`backups --pin=ID`, a button on the profile page; it does not count towards `keep`); a backup that a run is writing or a check is reading. A `faulty` or `incomplete` backup is **not deleted by retention** (it may be recoverable by hand; the dashboard says it is there). Leftovers of runs that died (work directories and `.part` files) that no run record and no lock claims and that are older than seven days are removed.
- **When:** after every successful backup of the profile, and by the trigger once per hour per profile (so that `maxAgeDays` works for a site that no longer produces backups). **Never after a failed backup**, and never when the listing of the storage is incomplete (the storage cannot be read).
- **Safety:** `threadsafe retention <profile> [--dry-run]` shows what would be deleted and why; the profile page shows the same as a preview; every deletion is an audit entry with the rule that caused it. The rules are applied oldest first, one backup at a time, and the numbers are recomputed after each deletion.

### 3.5 Encryption

**Format.** An encrypted part is the finished ZIP part wrapped in the **`age` v1 format** (`shop_..._p01.zip.age`). The ZIP inside stays an ordinary ZIP, so what has been decided in the earlier phases (archives open with ordinary tools) holds after decryption with an ordinary tool: `age -d -i key.txt shop_..._p01.zip.age > shop_..._p01.zip`. What the format gives, and what is implemented in PHP with `ext-sodium` (which is part of PHP 8.4):

- **Recipients:** X25519 public keys (`age1...`). A backup is encrypted for every recipient of the profile; any one of the keys opens it. The secret keys (`AGE-SECRET-KEY-1...`) belong to the owner and **never touch the server**, except as typed into the restore (3.5, "Restoring").
- **Streams:** the payload is cut into chunks of 64 KiB, each sealed with ChaCha20-Poly1305 under a key derived from the file key and a per-file nonce; the last chunk is marked, so truncation is detected. Because a chunk's nonce is its number, **a reader can jump to any chunk**: that is what lets `ZipReader` read an encrypted part without first decrypting it to a temporary file (below), and lets encryption stop and resume at a chunk boundary in a tick.
- **Keys, easy to keep:** `threadsafe keys generate` and the profile page make a key pair and present it so that it can be kept without effort: the secret key and the public key each with a **copy button** (the clipboard API where the page is https or local, otherwise the text is selected for copying by hand); a **file to download or save** (`--output=FILE` on the command line, mode 0600) with exactly the content of `age-keygen` (`# created: ...`, `# public key: age1...`, `AGE-SECRET-KEY-1...`), so that the real `age` tool opens it directly; and a **print view** (a page that prints cleanly, for a paper copy) that holds the secret key, the public key and the sentence that says what is lost without it. The owner stores the secret key somewhere safe and the public key goes into the profile. The page shows the secret key **once**; it is not stored on the server. The same for a **passphrase**: `keys passphrase` and a button next to the field offer a generated one that is easy to read aloud, type and copy - five groups of four letters and digits from an alphabet without look-alike characters (about 95 bits), e.g. `kr7m-xq3d-hp9t-w4nc-2vfe` - and show it once with the same copy button and file; a passphrase that the person chooses is accepted as well.
- **Passphrase (decided by spike 1a): the native `age` passphrase recipient, `scrypt` with N = 2^15, r = 8, p = 1.** `age` itself uses `scrypt` for passphrases with N = 2^18 (256 MB); in pure PHP that takes 21 s and 328 MB, too much for a request of 30 s and 64 MB. At N = 2^15 it takes 2.7 s and 42 MB in PHP, fits into the limits of a request, and the real `age -d` opens such a file (it accepts any work factor up to 2^22). Sealing needs the `scrypt` once per file key, at the start of a part. So the passphrase stanza is the standard one (`-> scrypt <salt> 15`) and no extension of the format is needed. A passphrase made by the program (about 95 bits) is safe at this factor; a short passphrase typed by a person is weaker, and the profile page and `keys` say so and recommend the generated one. *Opening* a backup that `age` itself sealed with its default N = 2^18 works on the command line (`restore` with a memory limit of 512 MB, about 21 s) but not in the wizard under 64 MB; the wizard says so by name and points to `age -d`. The fallback considered, a key pair derived from the passphrase with Argon2id (`sodium_crypto_pwhash`) as an ordinary X25519 recipient, is **not needed** and not built.

**In the backup.** A new stage `encrypt` follows the packing of each part: when a part is closed it is sealed into `<part>.age` in ticks (chunk by chunk, with the position and the stream's counters in the run state), the plain part is removed after the sealed one has been checked, and packing goes on. So at most one plain part is on disk at a time besides the sealed ones, and a plain part never lies in the storage after the run (it lies in the work directory, which is closed to the web like the storage). The file key of a part is random; it is wrapped for every recipient in the header of that part and, until the part is done, kept in the run state (mode 0600, deleted with the run), like the database password of a restore. A **passphrase typed for a web backup** is held the same way for the length of the run only. If the run fails, the sealed and the plain files are removed like any other leftover.

**What is stored where.**
- `…-pNN.zip.age` - the sealed part. The part marker and the manifest are inside the ZIP, so they are encrypted.
- The **sidecar file** of an encrypted backup (decision 3) is minimal: time, size, the parts with their SHA-256 *of the sealed file*, application and version, status, the number of files, directories and tables, `encryption`. No domains, paths, table names, filters, warnings with file names. The profile page and the details page show what that holds and say "details are in the encrypted archive".
- The web interface and the commands list, check (quickly), download and delete such a backup without a key.

**Checking.** Quick (size and SHA-256 of the sealed files) needs no key. A **full** check needs the secret key or the passphrase (`verify --identity-file=FILE` / `--passphrase-file=FILE`): it reads the ZIP *through* the decrypting stream and does everything it does for a plain backup, and the authentication tags of the chunks make the check stronger (every byte is authenticated, not only checksummed). The web interface does the quick check only and says so; it never sees a secret key. `threadsafe keys check` decrypts the first chunk of a part with a key to show that the key fits.

**Downloading** sends the sealed file unchanged ("encrypted archives are downloaded encrypted").

**Restoring.** `BackupSource` accepts `.zip.age` parts. `restore` takes `--identity-file=FILE` or `--passphrase-file=FILE`; the wizard asks for the secret key or the passphrase on the page where it asks which backup, keeps it in the run state like the database password (mode 0600, blanked at the last tick, deleted with the state) and says that it is sent over the connection (the plain-http confirmation of the wizard applies). The extractor and the importer read the ZIP through the **decrypting stream** (a PHP stream wrapper that implements `fread`, `fseek` and `ftell` over the chunks; the plain size is computed from the sealed size, so `ZipReader` finds the end record without reading; spike 1a has the prototype, `ZipReader::openFile` sets a read chunk of 1 MiB for a stream of a wrapper because PHP hands out only 8 KiB per `fread()` and the tail of an archive is read in one piece), so no decrypted copy of a multi-gigabyte part is written and the free-space check does not double. The preflight reads the manifest through the same stream. `restore.php` needs `ext-sodium`; the preflight says so when it is missing, in the sentence that names the extension.

**When the key is lost, the backups are lost.** The documentation says so before the first key is made, `keys generate` repeats it, and the profile form requires the person to tick that the secret key has been stored somewhere other than this server.

### 3.6 The interface and the command line

- **Command line:** `cron` (3.3), `retention`, `keys generate|derive|check`, `admin cron-secret`; `profile add|edit` get `--schedule`, `--keep`, `--max-age-days`, `--max-bytes`, `--recipient` (repeatable), `--no-schedule`, `--no-encryption`; `backup` gets `--passphrase-file`; `backups` shows the lock and the pin and `--pin=ID`/`--unpin=ID`; `verify`/`restore` get the key options of 3.5.
- **Profile form:** a *Schedule* section (the expression, a few presets, the next three runs shown in the configured time zone), a *Retention* section (three numbers and the preview of what the rules would delete now), an *Encryption* section (the recipients, "make a key pair" with the copy buttons, the file and the print view of 3.5, "suggest a passphrase", the tick that the secret key is stored elsewhere).
- **Dashboard:** "next run" on every card with a schedule, the last trigger and its warning in the header; a card shows a lock for an encrypted newest backup. **Profile page:** a pin button per backup, the state "encrypted" in the list, a passphrase field next to *Back up now* when the profile is encrypted.
- **System page:** the trigger (the crontab line, the address, the last heartbeat), the time zone, `ext-sodium` present or not, the retention that ran last.

## 4. Test strategy

### 4.1 Unit tests (no database, no network)

- **Cron:** a table of expressions and instants with the expected next and previous instants (lists, ranges, steps, names, both day fields, `@daily`, leap day, end of year); daylight saving time in `Europe/Berlin`, `America/New_York`, `Australia/Lord_Howe` (a half-hour shift) and `UTC`; malformed expressions refused with a message that names the field.
- **Scheduler:** due, not due, handled, skipped after the grace, one run made up after a long absence, retries after a failure and their limit, the queue order, a manual backup in the way, state files lost, a clock that went back.
- **Retention:** every rule alone and combined, the newest good backup kept whatever the rules say, pinned backups, faulty and incomplete ones left alone, leftovers only when old and unclaimed, the order, recomputing after each deletion, a dry run that deletes nothing, an unreadable storage that deletes nothing.
- **`age`:** bech32 encoding of keys against the published vectors; the X25519 stanza, the header MAC and the payload against the **test vectors of the `age` project (CCTV)** and against files made by the real tool; chunk boundaries (empty, one byte, exactly 64 KiB, 64 KiB + 1, many chunks); truncation, a flipped bit, a wrong key, a missing last-chunk mark all refused; random access (`fseek` to every kind of position) equal to a sequential read; the derived identity of a passphrase is stable and differs with the salt.
- **Trigger address:** a wrong or empty secret is the plain "not found"; the throttle; present with the interface off; absent without a secret; one tick per call.
- **The CLI tests** of `profile`, `backup`, `backups`, `verify`, `restore`, `admin` stay green after the extensions.

### 4.2 Integration tests (Docker)

The tools image gets the real `age` tool (`apt-get install age`), the oracle in both directions.

| Test | Proves |
|---|---|

## 6. Acceptance criteria

1. A profile with a schedule is backed up by the trigger at the scheduled time, by the command (snapshot) and by the address (under 5 s / 64 MB, table by table); never two backups at once; one call too many does nothing.
2. A long absence makes up one run if within the grace and skips it otherwise; a failing run is retried twice; a killed trigger is continued by the next call and gives an archive equal to an uninterrupted one.
3. The dashboard shows the next run of every scheduled profile and warns when the trigger stays away; the System page gives the exact line for the crontab and the exact address.
4. Retention keeps the rules of 3.4 on real backups, never deletes the newest usable backup or a pinned one, shows a dry run and a preview that agree with what it then does, and writes every deletion to the audit log.
5. An encrypted backup opens with the real `age` tool with the secret key and with the passphrase; the ZIP inside passes `unzip -t`; the server holds no secret key and no passphrase after the run; the sidecar file holds no domain, path or table name.
6. `threadsafe restore` and `restore.php` (through the wizard under 5 s / 64 MB) restore an encrypted backup into an empty target with equal tables and files; a wrong key is refused before anything is written; a truncated or damaged sealed part is found by the full check and by the restore.
7. The quick check, the list, the download and the deletion work on an encrypted backup without a key; the web interface never asks for a secret key except in the wizard of `restore.php` on the target.
8. Secrets (the cron secret, passphrases, secret keys, the file key) appear in no log, audit entry, report, manifest or page, except the one page that shows a freshly made key or passphrase once; the file key and a typed passphrase live only in the run state until the run ends.
9. A key pair or passphrase made by the program can be copied with one click, saved as a file that `age` itself accepts, and printed; the page that shows it says what is lost without it.
10. Unit tests, PHPStan level 8 and the integration tests (`tests/stack/matrix.sh`) pass on MariaDB 10.11, MySQL 8.4 and MariaDB 11.8; `composer test:bundle` passes (the restore tool carries the decryption).

## 7. Risks and decisions

**Risks**

- **Cryptography written by us.** The primitives are libsodium's; what is ours is the *composition* of the `age` format. Mitigation: the format is public and has test vectors; the real tool is the oracle in both directions; no invention (no own header, no own mode); the work package that writes it starts with the spike that proves the compatibility.
- **`scrypt` in PHP** is too slow at the work factor `age` itself uses (spike 1a: 21 s, 328 MB at 2^18). Resolved: the passphrase uses 2^15 (2.7 s, 42 MB), which `age` opens; a file that `age` sealed at 2^18 opens on the command line only.
- **`ext-sodium` is missing** on a host. Encryption and decryption are then unavailable and say so by name; nothing else changes. `host-probe.php` reports it (and its speed); the live host has it (section 8, finding 8).
- **A lost key means lost backups.** Documentation first, the tick in the form, `keys check`, and the sidecar that says which public keys a backup was made for (their short fingerprints) so that the right secret key can be found.
- **The restore tool carries more code** (the decrypting stream, bech32, X25519 handling). The bundle grows by a few tens of KB; `composer test:bundle` runs the tests against it.
- **Retention deletes what a person wanted.** Never the newest usable one, pinned ones are safe, faulty ones are left, a dry run and a preview exist, every deletion is audited; and the first run of a new rule on a profile that has more backups than `keep` shows the list and waits for one confirmation (command and page) before the trigger applies it on its own.
- **Time zones and daylight saving time** are where schedulers go wrong. A test table per zone, a fixed rule for both kinds of gap, and the time zone shown next to every instant in the interface.
- **Two triggers at once** (the cron job and a monitoring service call the address): the instance lock, the active-run rule and one tick per call make that harmless; a test calls the address in parallel.
- **A host that kills long cron processes or detached workers.** The next call continues the run from its saved state; the manifest says `consistency: table`; the documentation recommends a call every few minutes and says what the host's limits do to a long backup. With one call a day and a host that cuts a worker after some minutes, a big backup would need days: the System page then says to call more often (from another server) or to switch to tick mode.
- **A worker that starts itself.** Spike 1c produced it once (a child that inherits the CGI environment): the worker is started only with a clean environment, only while `cron.lock` is free, never from the worker itself, and a test counts the processes.
- **The secret in the address** is logged by the web server. It grants nothing but the start of a backup; it can be replaced; the documentation says so.
- **Scope.** Three features, each with a command, a page and a restore path. They are separate work packages with their own proof, and the order lets the owner stop after milestone A or B.

**Decisions** (1-3 settled in answer to questions; 4-12 proposed and confirmed, with the addition to 9)

1. **Format - settled (2026-10-22):** encrypted archives are `age` files around the ZIP parts (`.zip.age`); rejected: ZIP AES (no key pair, slow in PHP, file names visible), an own format.
2. **Keys for backups made by hand - settled (2026-10-22):** the public keys of the profile are used for every backup, scheduled or manual; the web interface can add a passphrase for one backup, held only in the run state until the run ends. The command line has `--passphrase-file`.
3. **Metadata - settled (2026-10-22):** the sidecar file of an encrypted backup is minimal (3.5).
4. **Passphrase realisation - settled (2026-10-22):** native `age` passphrase if spike 1a shows a safe work factor within the limits of a request, otherwise a derived identity (3.5). **Outcome of the spike (2026-10-22): the native `age` passphrase recipient, `scrypt` N = 2^15**, as 3.5 says; the derived identity is not built.
5. **Trigger - settled (2026-10-22):** `threadsafe cron` and `/cron/<secret>` as in 3.3; the address exists only with a secret and independently of `web.enabled`; the command is preferred and documented first, **but where the host's cron can only fetch an address (the customer host: HTTP GET, once a day), the address starts a detached worker** (3.3, amended after spike 1c) and a second server calling every minute is only the fallback for tick mode.
6. **Schedule semantics - settled (2026-10-22):** five-field cron expressions in one configurable time zone; grace of six hours; two retries at 15 minute intervals; one backup at a time; a missed run is made up once.
7. **Retention - settled (2026-10-22):** the three rules, the newest usable backup and pinned backups protected, faulty ones left, old unclaimed leftovers removed after seven days, a first-time confirmation for a rule that would delete many (3.4, risks).
8. **Scheduled backups are CLI tasks when called by the command - settled (2026-10-22), amended (2026-10-22, after spike 1c):** snapshot consistency; when called by the address they are CLI tasks as well if the address can start a detached worker (the default, `cron.mode` `auto`), and web tasks with `consistency: table` only in tick mode. The owner's customer host allows nothing but one HTTP GET a day, which is why the worker exists.
9. **Secrets - settled (2026-10-22), as proposed with one addition:** secret keys and passphrases are never stored on the server; a file key and a typed passphrase live in the run state (0600) only for the length of the run; the key pair or passphrase made by the program is shown once, **and is easy to keep: copy buttons, a file in the format of `age-keygen`, a print view** (3.5).
10. **Restore of encrypted backups - settled (2026-10-22):** in this phase, in the command and in `restore.php`, through a decrypting stream, without a decrypted copy on disk; `restore.php` needs `ext-sodium`.
11. **Encryption is per profile - settled (2026-10-22):** switching it on affects the backups made afterwards; older ones stay what they are; one storage may hold both kinds.
12. **Out of scope - settled (2026-10-22):** remote storage and notifications stay for a later phase; `Postproc` is not changed.

## 8. Findings of work package 1 (spikes)

The scripts are in `tools/spikes/` (`age-format.php`, `scrypt-php.php`, `age-passphrase.php`, `cron-next.php`, `idle-trigger.php`, `cron-lifetime.php`, and `host-probe.php` extended). They run in the `tools` container (PHP 8.4, libsodium 1.0.18, `age` 1.2.1 - the tools image now installs `age`, the oracle of the later tests). Each finding that changes the design is also corrected in the text of the section it concerns.

**1. The `age` v1 format is implementable in PHP with `ext-sodium`, and the real tool agrees in both directions** (`age-format.php`). Bech32 keys: the public key of a secret key equals what `age-keygen` writes, and `age-keygen -y` on a key we made prints the same. Files of 0, 1, 15, 16, 17, 65535, 65536, 65537, 131072, 131073, 196608 and 200001 bytes: `age -d` opens ours and we open `age`'s. Refused, as they must be: a flipped bit in the payload, a cut after a whole chunk, a cut inside the last chunk, a wrong key. What is not yet done: the test vectors of the `age` project (CCTV) were not used, only the real tool; they go into the unit tests of work package 5 (4.1).

**2. Speed is no problem.** 128 MB: sealing 0.13 s (about 950 MB/s), opening 0.10 s (about 1300 MB/s); `age` itself needs 0.12 s. The cost of encryption in a backup is the reading and writing of the parts, not the cipher.
**3. A seekable decrypting stream works under `ZipReader`** (`AgeDecryptStream`, a stream wrapper with `fread`, `fseek`, `ftell`, `fstat`). The plain size follows from the sealed size (from the payload after the header and the 16-byte nonce: whole chunks of 65,552 bytes, and a rest that is the last chunk minus its 16-byte tag), so the end record of the ZIP is found without reading the file. A ZIP of 19.2 MB with 200 entries: verification through the stream 0.19 s (the plain file 0.03 s), no problems; one entry from the middle 1.5 ms and equal to the original. **One correction in the code:** PHP's stream layer hands out at most one read chunk (8 KiB by default) per `fread()` on a wrapper, and `ZipReader` reads the tail of an archive in one piece and then thought the end record was missing. `ZipReader::openFile` now sets a read chunk of 1 MiB for a stream that is not a plain file (`stream_set_chunk_size`); this is the only change to existing code in this work package (the unit tests of `ZipReader` and the whole check are run against it). Reading a plain file is untouched. A unit test (`ZipReaderTest`, with the wrapper `tests/Support/ChunkedStream`) pins it: it fails with "no end record" without the line and passes with it.

**4. The passphrase: the native `age` passphrase recipient at N = 2^15** (`scrypt-php.php`, `age-passphrase.php`). Pure PHP scrypt (r = 8, p = 1; the RFC 7914 vector passes): 2^10 0.09 s / 2 MB, 2^12 0.33 s / 6 MB, 2^14 1.3 s / 22 MB, **2^15 2.7 s / 42 MB**, 2^16 5.3 s / 84 MB, 2^18 (the default of `age`, measured by opening a real file) **21 s / 328 MB**. `age -d` opens a file whose scrypt stanza says 2^15 and we open `age`'s own files (which use 2^18) with the right file key - at 328 MB, so on the command line only. The rule of decision 4 therefore gives the native passphrase, and the Argon2id fallback is not built (it stays a possibility if a host needs a higher factor: it would not change the file format, only add a recipient). The price: 2^15 is eight times cheaper to attack than the default; the passphrase made by the program has about 95 bits and is not endangered by that, a weak typed passphrase is.

**5. Cron arithmetic: our own rule, checked against PHP over a year** (`cron-next.php`). A prototype `Cron` (five fields, lists, ranges, steps, names, both day fields restricted = either, the shortcuts) gives the next instant after a given one. Hand-checked on 8 expressions; compared by brute force, minute by minute over 2026, with `DateTimeZone` on 55 combinations of zone (UTC, Europe/Berlin, America/New_York, Australia/Lord_Howe with its half-hour shift, Asia/Kolkata with its half-hour offset and no daylight saving time) and expression: **0 unexplained differences**. The explained ones are exactly the two daylight saving cases: the second pass of a repeated hour (by rule not run) and the first instant after a gap (by rule run once). PHP alone cannot be trusted for these: it resolves a repeated local time to the second occurrence in Berlin and to the first in New York, and moves a time that does not exist forward by the gap. Hence the explicit `resolve()` (3.2). `ext-calendar` is not installed in the containers, so the prototype counts the days of a month itself. A chain of 35,000 `next()` calls takes 0.7 s, so even a minute-by-minute expression is cheap.

**6. An idle trigger call is cheap** (`idle-trigger.php`, 10 and 50 profiles with 50 and 100 backups each, sparse part files). Reading the profiles 0.3 to 1.3 ms; listing only the **names** of every storage 4.8 ms (10 profiles with 50 backups: 1,000 files) and 49 ms (50 profiles with 100 backups: 10,000 files); listing with the sidecars read (the work of the dashboard's `Overview`) 41 ms and 239 ms. Memory peak 4 to 6 MB. The start of the command in the container costs 130 to 150 ms in total (13 ms for a bare PHP; the rest is the autoloader and the commands, slowed by the mounted drive of the container). Conclusion: the scheduler reads names and state files only, never the sidecars, and needs no index (3.3). A call every minute costs a host well under a second of CPU, mostly the start of PHP.

**7. What the host probe now tells** (`host-probe.php`, new sections "Encryption" and "Trigger"): whether `sodium` is loaded and works (ChaCha20-Poly1305, X25519, `hash_hkdf`) and how fast it seals 8 MB; the default time zone; `curl`, `allow_url_fopen`, `openssl`; which of `curl`, `wget`, `timeout`, `flock`, `crontab` the shell finds; and whether the host can fetch a page **from itself** by its public address (the case of a cron job that calls `/cron/<secret>`). It answers its own request (`&ping=1`) so that it needs nothing installed. Tried in the container, on the command line and behind PHP's built-in web server (with four workers, because a single worker would wait for itself).

**8. The customer's host: a call can start a detached worker, and it lives on** (runs of 2026-10-22 on the live host, the owner's). Its cron may only fetch an address with HTTP GET, at most once a day. `host-probe.php`: PHP 8.4.27 as `cgi-fcgi` (`/usr/lib/cgi-bin/php8.4`, also `/usr/bin/php8.4`), 30 s and 512 MB per request, `exec` and `proc_open` allowed, `sodium` 1.0.18 (ChaCha20-Poly1305 at 442 MB/s, so `restore.php` can open encrypted backups there), `curl`, `wget`, `flock`, `timeout` and `crontab` found, fetching its own address works (0.6 s), an Argon2id hash takes 2.9 s (the login of the interface). `cron-lifetime.php?mode=spawn` started `setsid nohup /usr/bin/php8.4 -q cron-lifetime.php N` with standard input `/dev/null` and a clean environment from a web request; the request ended at once and the process **lived on for 123 s and for 902 s (15 minutes) with nothing cutting it off**; `set_time_limit(0)` took effect (30 → 0); its memory limit is 512 MB. Not tested: processes longer than 15 minutes, and heavy CPU for long (the spike calculated a little every 10 s), in case the host counts CPU time. So worker mode (3.3) is possible on this host: one call a day starts `threadsafe cron`, which then works without the limits of a request, with `consistency: snapshot`.

**9. Two traps on the way - both the spike's own bugs, both now rules** (they cost an hour and, once, a runaway). (a) *A child that inherits the CGI environment.* The first spawn did not clean the environment; the CGI binary took the inherited `REQUEST_METHOD` and `QUERY_STRING` for a request, ran the spawn branch again, and started itself 1,014 times in 3 minutes 17 seconds, until the host ended it (a later `ps` found no process left; the script only writes a log). **Rule: a worker is started with `env -i PATH=...`, from the lock-protected trigger only, and never by the worker itself; a test counts the processes (3.3, risks, 4.2).** The spike now also refuses a second spawn within a minute. (b) *`PHP_SAPI` is `cgi-fcgi` for a script started from a shell as well.* The second version took the child for a web request and ended silently, because its output went to `/dev/null`. The program already decides as `Budget::isCommandLine()` does (a `cgi*` SAPI without `REQUEST_METHOD` is a command line) and `bin/threadsafe` already calls `set_time_limit(0)`, so nothing in `src` changes; **the worker's output goes to a file under `data/`**, so that a worker that dies at once leaves its reason.

**10. A trigger that comes once a day sets the rhythm of the schedule.** The scheduler runs a profile when it is due at the call (3.2): the latest scheduled instant, at most the grace (six hours) ago. With one call at 03:05 a day, a profile scheduled `0 3 * * *` runs, a profile scheduled `30 3 * * *` does not (the instant is not yet reached) and its instant of the day before is long past the grace, so it would never run. The rule for the documentation, the profile form and the System page: **the time of the host's cron must lie after the scheduled time and within the grace**, and a schedule that is more frequent than the trigger is warned about ("the trigger comes every 24 hours, this profile is due every hour"), using `schedule.expectedIntervalMinutes` (1,440 on this host). Nothing else changes.

**Left open (nothing in the plan waits for it):** the private test of a real backup, and worker runs longer than 15 minutes or heavier than the spike's, which a first real backup on the customer's host will show; the worker's log file tells how it ended.

## 9. As built

### Work package 2: the schedule core

**What exists.** `src/Schedule/`: `CronExpression` (`parse`, `next`, `previous`), `Scheduler` (`plan`, `next`, `started`, `succeeded`, `failed`, `skipped`, `reset`, `forget`), `ScheduleState` and `ScheduleStore` (`data/schedule/<profile>.json`, mode 0700 for the directory), the results `SchedulePlan`, `DueRun`, `SkippedRun`, and `ScheduleException`. `src/Profile/`: the value classes `ScheduleSettings`, `RetentionSettings` and `EncryptionSettings`, and the three optional fields `schedule`, `retention` and `encryption` of `SiteProfile` (absent or `null` = none; a profile without them is stored without them, so existing profile files read and write as before). `ProfileService::store()` and `remove()` keep the scheduler's state in step with the schedule (3.2, "counts from the moment it is set"). `Config` has `schedule.timezone`, `schedule.graceMinutes`, `schedule.expectedIntervalMinutes` and `cron.mode` with accessors (`scheduleZone()` ...); `threadsafe admin set KEY VALUE` changes a setting (audit entry `settings.changed`, key only). `profile add|edit` take `--schedule`, `--no-schedule`, `--keep`, `--max-age-days`, `--max-bytes`, `--no-retention`, `--recipient` (repeatable) and `--no-encryption`; `profile show` prints the schedule with the time zone and the next run, the rules, and the keys shortened.

**Where it differs from the plan.**
- `CronExpression::previous()` is not only the mirror of `next()`: asked from the second pass of a repeated hour it returns the **last due instant of the first pass** (found by the property test, which checks `next(previous(a)) > a` and `previous(next(a)) = next(a)` across every transition of three zones). The shortcuts are the four of the plan (`@hourly`, `@daily`, `@weekly`, `@monthly`); an expression that never matches a date (31 February) is refused when it is parsed. A field that starts with `*` counts as unrestricted also with a step (`*/2` in the day field), as in Vixie cron; the prototype of the spike got that wrong for a step in the day fields.
- The **state is keyed by "since"** (3.2): the plan had only the last handled instant. `Scheduler::plan()` writes the state of a profile it sees for the first time; otherwise it only reads.
- **`cron.secret` is not in `Config` yet.** `Config` is documented as holding nothing secret (it is shown on the System page); where the secret lives (a file of its own, 0600, next to `admin.json`, or its hash plus the shown value) is decided with `admin cron-secret` in work package 3.
- **`admin set`** and **`--no-retention`** are small additions that the plan did not list: without a page for the settings there was no way to set the time zone, and a retention that cannot be removed again is a trap.
- **The profile form does not show the new fields.** It builds the profile from the form alone, so editing a profile in the browser would have dropped them (the test fails without the line that carries them over). The form fields come with the work packages that make them useful (3, 4 and 6).

**Proof.** 114 new unit tests: `CronExpressionTest` (66: hand cases, refused expressions, the transition table for Berlin, New York and Lord Howe with half-hour shifts, the property test with about 89,000 assertions, a chain of 20,000 instants that must take under 5 seconds), `SchedulerTest` (14: the first sighting, grace, a pile of missed days giving exactly one run, retries and giving up, a retry past the grace, the order of the queue, change of schedule, lost or damaged state, time zones, the second pass of a repeated hour), `ScheduleStoreTest`, `SiteProfileTest` (round trip, refusals), `ProfilePagesTest` (editing in the browser keeps the fields), `ProfileServiceTest` (the state follows the schedule), `ProfileAndBackupCommandTest` and `AdminCommandTest` (the options, the mistakes, `admin set`), `ConfigAndStoresTest`. `composer check` (lint, PHPStan level 8, 2565 unit tests, the same tests against the bundle) is green. **Not done:** the web form fields, the dashboard's "next run", the trigger itself (work package 3), the retention (4).
