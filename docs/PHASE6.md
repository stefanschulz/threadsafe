# Phase 6 – the website type Joomla

**Status:** **in progress** (2026-10-23; the decisions of section 7.2 were settled with the owner the same day; work package 1, the spikes, is done: sections 8 and 9).
**Context:** [CONCEPT.md](CONCEPT.md) section 3.4 (website types: "new types arise by extending `generic` with detection, filter defaults and restore steps") and section 4 (the PrestaShop restore, the model for what a type adapts after a restore); [BACKUP.md](BACKUP.md), [RESTORE.md](RESTORE.md), [MIGRATE.md](MIGRATE.md) and [WEB.md](WEB.md) describe what this phase extends; `plugins/generic` (the smallest type) and `plugins/prestashop9` (the largest) are the two examples in the code. The facts about Joomla below come from the Joomla project's documentation and from hosting guides (section "Sources"); what could be seen in a real installation was checked in work package 1 (section 8); what is still unchecked is marked **verify**.

## 1. Goal and scope

A site profile can say **`joomla`**: ThreadSafe then recognises a Joomla installation, reads the database access from its `configuration.php` without starting Joomla, leaves out what Joomla rebuilds (caches, sessions, logs, the search index), writes what a restore needs to know into the manifest, and **after a restore or a migration** makes the site work on its new domain, path, database and directory - the way it does for PrestaShop 9. Backups of a Joomla site are standard archives like every other (files plus one SQL file per table); nothing about the format changes.

| In scope | Out of scope (later) |
|---|---|
| detection of Joomla 5.x and 6.x from the files; the database access from `configuration.php` (read, never executed); the database types `mysqli` and `pdomysql` (MariaDB and MySQL) | Joomla 4 and older (end of life; decision 1 of section 7.2); a Joomla with `dbtype` `pgsql` (refused with a clear message) |
| default filters: caches, temporary files, logs, sessions, the Smart Search index, the archives of other backup extensions; the manifest with version, table prefix, address, extensions, templates, languages | rules per extension (like the module rules of PrestaShop: extensions that store the domain in files or in their own tables); Joomla multi-site set-ups; the `Joomla Update` through ThreadSafe |
| restore and `threadsafe migrate joomla` on another domain, in another directory or sub-directory, with another database or table prefix: `configuration.php`, `.htaccess`, the old address in the content of the database, caches, sessions, a self-test | restoring over an existing installation (a general gap, [RESTORE.md](RESTORE.md) section 9) |
| the type in the web interface (profile form, the restore wizard of `restore.php`), the command line and the documentation | WordPress (a type of its own, a later phase; this phase shows what a type needs) |
| a **dev mode** for a live -> dev copy, in a small first cut (section 3.6) | the full set of dev-mode rules |

Phase 6 ends with the **proof on the Docker stack** (a real Joomla, backed up, restored on another domain and path with the plain tools, with `threadsafe restore` and with the `restore.php` wizard under 5 seconds and 64 MB, on MariaDB 10.11, MySQL 8.4 and MariaDB 11.8) and with a **field test** by the owner on a real Joomla site (the same way as the private test with the live PrestaShop shop, [BACKUP.md](BACKUP.md) section 10).

## 2. Deliverables

1. `plugins/joomla/` with `plugin.json` (id `joomla`, title "Joomla") and the classes of the three capabilities (`Backupable`, `Restorable`, `WebsiteType`), registered like the other two types; the web interface, the commands and `restore.php` find it without a change of the core (`restore.php` bundles every plugin).
2. A **reader and a writer for `configuration.php`**: read by a tokenizer, never executed, with the same care as `ParametersParser` of PrestaShop; written back changing only the values that the restore sets and keeping every other byte (the file holds secrets, and sites add their own properties).
3. The migration steps of the type (read the state, write the configuration, replace the old address in the database, rewrite `.htaccess`, discard caches and sessions, self-test) and the options of `migrate joomla`.
4. The Docker stack for Joomla (a source site, the empty target that the existing target stack provides) and a seed with problem cases; integration tests in groups; the matrix on the three database servers.
5. Unit tests for everything that needs no database: the configuration reader and writer, detection, filters, the address detection, the `.htaccess` rewrite, the domain replacement on Joomla's JSON.
6. `docs/JOOMLA.md` (the user documentation: what is backed up and left out, what a restore adapts, what stays manual, the limits), the changes to `README.md`, `AGENTS.md`, `WEB.md`, `RESTORE.md` and this plan's "As built" section.

## 3. Design

### 3.1 What a Joomla installation looks like (to verify in work package 1)

| Fact | What the type does with it |
|---|---|
| **Versions.** Joomla 4 reached its end of life on 2025-10-14; Joomla 5 gets security fixes until 2027-10-12; Joomla 6.0 came out on 2025-10-14 and needs PHP 8.3, MariaDB 10.4 or MySQL 8.0.13 at least (dates from secondary sources, **verify** on the project's lifecycle page). | Detect 5.x and 6.x as one type, `joomla` (the layout of `configuration.php` and of the tables is the same across them; the version goes into the manifest, not into the id). `restoreChecks` refuse a version outside this range, and refuse a target PHP or database server below what the backed-up Joomla needs. Joomla 4 is end of life and is left out (decision 1). The PHP minimum of each is in `libraries/vendor/composer/platform_check.php` (8.1 for 5.4, 8.3 for 6.2). |
| **Version** is in `libraries/src/Version.php` (`public const MAJOR_VERSION`, `MINOR_VERSION`, `PATCH_VERSION`, `EXTRA_VERSION`; confirmed in 5.4.8 and 6.2.0). | `detect()`: read the constants from the file by a tokenizer (never include the file), together with the presence of `configuration.php`, `administrator/index.php`, `libraries/`. |
| **`configuration.php`** is a PHP class `JConfig` with one `public $name = 'value';` per setting: `dbtype` (`mysqli`, `pdomysql`, `pgsql`), `host` (with the port as `host:3306`, or a socket), `user`, `password`, `db`, `dbprefix`, `live_site` (usually empty), `secret`, `log_path`, `tmp_path`, `cache_path`, `sef`, `sef_rewrite`, `offline`, `mailonline`, `smtppass` ... (the same 67 properties in 5.4 and 6.2, section 8). | The database access comes from here. The file holds **secrets** (database and SMTP passwords, `secret`): they never go into a log, a report, the manifest or a page, like `parameters.php` of PrestaShop. |
| **The absolute paths** `log_path`, `tmp_path` (and `cache_path` where set) are written at the installation and name the directories of the old host. | A restore on another path sets them to the new ones (otherwise Joomla complains that `tmp` is not writable). |
| **The address of the site** is stored nowhere as a single value: `live_site` is mostly empty, and Joomla takes the address from the request. The old address is in the **content** (articles, modules, menus, template styles, the parameters of extensions - mostly JSON, so `https:\/\/` with escaped slashes). | This is the one design question of the type: where does the "old domain" of a restore come from? See 3.4 and decision 2. The replacement itself is what `generic` already does for every text column (serialized PHP and JSON stay valid). |
| **`.htaccess`** is the file `htaccess.txt` of Joomla copied under that name; `RewriteBase` is usually commented out; sites on Apache with search-engine friendly addresses depend on it. `web.config` is its IIS twin. | Rewrite `RewriteBase` and the base path when the site moves to a sub-directory or out of one; leave the rest; never touch `web.config` (out of scope, reported). |
| **Volatile data:** the directories `cache`, `administrator/cache`, `tmp`, `administrator/logs` (and `logs`); the tables `#__session`, `#__user_keys`, `#__updates`, the Smart Search index (`#__finder_*`, large), `#__action_logs` (the user actions log, can be large), the scheduler and mail logs (the names are confirmed in 5.4 and 6.2, section 8). | Default filters (3.3). Akeeba Backup, the most used Joomla backup extension, leaves out the sessions table and the Smart Search term and taxonomy tables by default for the same reason. |
| **Other backup extensions keep their archives inside the site** (for example `administrator/components/com_akeebabackup/backup`). | Left out by default: a backup must not contain the backups. |
| **A `configuration.php` that is read-only** (mode 0444 and owned by the web server's user, as the Docker images have it and many hosts) cannot be rewritten. | The writer **replaces** the file (a temporary file and a rename, `AtomicFile`), which works for mode 0444 and keeps that mode; it fails only if the directory is not writable, and then the restore says so and leaves no half-adapted site. (Built in work package 2; no `chmod` is needed.) |

### 3.2 The reader and the writer of `configuration.php`

`JoomlaConfigFile` (the reader) tokenizes the file: it finds the class `JConfig` and takes every `public $name = <literal>;` where the literal is a single- or double-quoted string without interpolation, a number, a boolean, `null` or an array of those. Anything else (a constant, a function call, a heredoc) is reported as "not understood", not guessed; the properties the type does not need may stay unparsed. It never `include`s the file.

`host` has three shapes: `name`, `name:port`, and a socket (`:/path/to/socket` or `localhost:/path`); an IPv6 address in brackets. The first two map to the `host` and `port` of `DatabaseSettings`; **a socket is not supported yet** and is reported with the setting to change (risk 5). `dbtype` `mysqli` and `pdomysql` map to the PHP interface setting (`auto` is the profile default); `pgsql` is refused.

`JoomlaConfigFile` is also the writer (like `ParametersFile` of PrestaShop; one class, immutable, every `with...()` returns a new instance): it replaces the **literal of named properties** in place and leaves everything else byte for byte, including the line ending style and the comments; a property that does not exist is added before the closing brace of the class. It is used only by the restore (3.5).

### 3.3 What a backup leaves out

In `plugins/joomla/resources/backup-defaults.json`, in the style of the PrestaShop file (paths relative to the site root, tables without the prefix):

- **paths** (whole directories): `cache`, `administrator/cache`, `tmp`, `administrator/logs`, `logs`, `.git`, and the output directories of other backup extensions (`administrator/components/com_akeebabackup/backup`, `administrator/components/com_akeeba/backup`). The restore makes `tmp`, `cache`, `administrator/cache` and `administrator/logs` again, empty (`EnsureSkeleton`, 3.5): Joomla's pages work without them (work package 1 took each away), but everything that writes there fails;
- **structure only:** `session`, `user_keys`, `updates` and the big tables of the search index: `finder_links`, `finder_links_terms`, `finder_logging`, `finder_taxonomy_map`, `finder_terms`, `finder_tokens` and `finder_tokens_aggregate` (the last two use the MEMORY engine). **`finder_taxonomy` keeps its data**, and so do `finder_types`, `finder_filters` and `finder_terms_common`: the ROOT row of `finder_taxonomy` is needed, and without it the Smart Search indexer stops with `MapTable::_getNode(1, id) failed` (work package 1). `action_logs` is kept (decision 5).

The profile can add to both lists or switch the defaults off, as for every type.

### 3.4 The manifest, and where the old address comes from

`manifestExtras()` writes, without ever failing when the database is missing: the version, the table prefix (not the password), the database type, `live_site`, the site name, the language list, the templates (name, whether site or administrator) and the **extensions** (type, element, version, enabled; third party ones are what a restorer wants to know about), and a list of **address candidates**.

The old address is found in this order (decision 2): (1) `live_site`, if set; (2) the address the owner typed in the profile (a new optional field of the type, asked at "Look at the site" and shown with the candidates); (3) the **candidates found in the content** at backup time: the hosts that occur in absolute URLs in the content columns (`#__content`, `#__modules`, `#__menu`, `#__template_styles`, `#__extensions`) counted by frequency, so that the most frequent one is proposed and the others are shown. The candidates are a proposal: the restore form asks for the old domain, pre-filled, and the replacement runs only when it is filled. Nothing is replaced on a guess.

### 3.5 The restore and the migration

The adaptation after the files are in place and the database is imported is a migration (as for PrestaShop: the type's steps run from `restore` as well as from `migrate joomla`). Steps, in order, each one a `Step` with a report line:

1. **ReadJoomlaState:** `configuration.php` read, version, prefix, `live_site`, the old address (from the request or the manifest), the database reachable, the prefix present in the database (tables named `<prefix>extensions` ...). A prefix that does not match the tables is an error, not a guess.
2. **WriteConfiguration:** `host`, `user`, `password`, `db` (and `dbprefix` when the restore changes it) from the request; **`dbtype`** `mysqli` or `pdomysql` by what the PHP of the target has (the PrestaShop image of the stack has `pdo_mysql` and no `mysqli`; `pdomysql` runs Joomla 5.4 and 6.2 as well); `log_path` and `tmp_path` set to the new directories when they differ (`cache_path` is not in 5.4 and 6.2); **`live_site`**: a stale value breaks the site (the front page answers with a redirect, section 8), so if it was set it is rewritten to the new address and cleared when no new address is known; `cookie_domain` and `cookie_path` only if set; **`secret` is kept** (it signs sessions and tokens; changing it logs everybody out and is not needed). With a table prefix change (an option, as in [RESTORE.md](RESTORE.md)) the prefix is set in the same step.
3. **ReplaceContentDomains:** the generic replacement of the old by the new address in every text column, plus what Joomla needs on top: the forms in JSON with escaped slashes (`https:\/\/old.example`), with and without the scheme, and the path change when the base path differs (`/old-dir/` to `/`); the tables that never get it (sessions, logs) are skipped. A dry run reports the number of rows it would change per table.
4. **RewriteHtaccess:** `RewriteBase` and the base path, as 3.1 says.
5. **EnsureSkeleton and DiscardCaches:** make `tmp`, `cache`, `administrator/cache` and `administrator/logs` where they are missing (each with the `index.html` placeholder that Joomla ships), empty them where they are not; truncate `#__session`; clear `#__updates` (the update information is fetched again).
6. **ApplyDevMode** (only with `--dev`, 3.6).
7. **SelfTest:** the front page answers 200 and carries the Joomla generator tag (unless the site turned it off, then only the status), `/administrator/` answers 200 with its login form, the site is not in offline mode by accident, and the database answers a query on `#__extensions`; reported as ok, warning or failure like the PrestaShop self-test.

`restoreChecks()` (before anything is written): the Joomla version is one of 4.4, 5 or 6; the PHP of the target satisfies the Joomla version (6.x: 8.3 at least); the database server of the target satisfies it (MariaDB 10.4 / MySQL 8.0.13 for 6.x); a backup made on MySQL 8 with the collation `utf8mb4_0900_ai_ci` is refused on MariaDB as everywhere else ([RESTORE.md](RESTORE.md) section 9); the PHP extensions that Joomla's own installer checks are present on the target (`json`, `zlib`, `xml`, `mbstring` and a database driver, `mysqli` or `pdo_mysql`, as errors; `gd`, `iconv`, `zip` and `intl` as warnings; section 8).

Fields of the restore form (`Restorable::fields`): the old address (pre-filled from the manifest), the new address, the base path (sub-directory), and the dev-mode switch; the values every restore needs (target directory, database) are the core's.

### 3.6 Dev mode, in a small first cut

For a live -> dev copy: `offline` stays as it is; `robots` set to `noindex, nofollow`; outgoing mail switched off (`mailonline` false) so that a copy does not send mail to customers; the site name gets a visible mark ("[DEV]"); an `.htaccess` block that sends `X-Robots-Tag: noindex`. Everything the PrestaShop dev mode does with module rules (payment, analytics, cron) is extension knowledge and stays **out** until the rules for extensions exist.

### 3.7 The interface and the command line

- `profile add --type=joomla` (type list from the registry: nothing to change); "Look at the site" shows "Joomla 5.2.3 found in /path", the database access read from `configuration.php` (no password), what is left out by default and how many tables are structure only, and the address candidates.
- `migrate joomla` with the common options of the command and the type's own (`--base-path`, `--dev`); `restore` and the `restore.php` wizard ask the fields of 3.5; `docs/JOOMLA.md` says what each one does.
- Nothing in `src/Admin` changes except what the registry gives for free; the profile card shows the title "Joomla" and the application "Joomla 5.2.3" from the manifest.

## 4. Test strategy

### 4.1 Unit tests (no database, no network)

- **The configuration reader:** the real `configuration.php` files of fresh installations of 5.4 and 6.2 (values replaced by test values, `tests/fixtures/joomla/`, made in work package 1), and variants made from them, a file with extra properties, with double-quoted strings, with comments, with CRLF, with `host` in all three shapes, with `pgsql`; a file that does not parse is reported, never executed (a fixture that would write a marker file when included proves it).
- **The writer:** the same files with each property changed; the bytes outside the literal are identical; a read-only file; a property that is missing is added.
- **Detection:** trees built in a temporary directory (a `Version.php` with the constants, without `configuration.php` (not installed), Joomla 4 and 3 (refused), WordPress (no)).
- **Filters and manifest extras** against a fake `Connection`; the address candidates on text with escaped slashes, sub-directories, `www.` and without it.
- **The `.htaccess` rewrite** on the file Joomla ships and on sites' variants; **the domain replacement** on Joomla's JSON (the generic step's tests already cover serialized data).
- **The checks** of the restore against a manifest of each version, a target PHP and a target database that are too old.

### 4.2 Integration tests (Docker)

A **Joomla service** in `.docker/docker-compose.yml` (the official images `joomla:5.4-php8.3-apache` and `joomla:6-php8.4-apache`; there is no PHP 8.4 image of Joomla 5), on the existing `db` service with a database of its own, installed by the image's own installer (the variables `JOOMLA_DB_HOST`, `JOOMLA_DB_USER`, `JOOMLA_DB_PASSWORD`, `JOOMLA_DB_NAME`, `JOOMLA_SITE_NAME`, `JOOMLA_ADMIN_*` worked in work package 1), then seeded with `tests/fixtures/seed-joomla-problem-cases.sql`: absolute URLs in articles (plain, with `www.`, as `<img>` and `<a>`), in module and template-style parameters (JSON with escaped slashes), in menu links and redirects; a foreign domain and an e-mail address that must **not** be replaced; some sessions and action-log rows; a table of an "extension" with another prefix; a second language. The empty target is the one the PrestaShop stack already has (Apache and PHP 8.4 in an isolated network; its PHP has what Joomla needs except `mysqli`, which is why the restore sets `dbtype`).

Groups, run by `tests/stack/run.sh` as new phases and by `matrix.sh` on the three servers:

1. **joomla-backup:** the profile is detected from the container's files, the backup of the seeded site, `verify`, the archive opened with `unzip -t`, the SQL file imported with the plain `mariadb` client and the tables compared with `CHECKSUM TABLE`; what is left out is absent, the structure-only tables are empty, `configuration.php` is in the archive and its password is not in any log or report.
2. **joomla-restore:** the backup restored by `threadsafe restore` into the empty target on another domain, in a sub-directory, with another database and another prefix: the site answers, the administrator logs in (the seeded administrator's password is a test value), an article shows with its images, the old address is nowhere in the content, the foreign domain is untouched, `secret` is unchanged.
3. **joomla-wizard:** the same through the `restore.php` wizard under 5 s and 64 MB (the stack's `web` service), with the key typed in for an encrypted backup.
4. **joomla-disaster:** the target destroyed and rebuilt, the site brought back through the wizard on the same address.
5. **The web interface:** the type in the profile form and the card, in the existing `web-ui` group.

### 4.3 The field test

By the owner, on a real Joomla site: a backup, a restore on another domain on a test host, a look at the front page and the administration, and the list of extensions that did something unexpected (it becomes the first entries of the extension rules of a later phase).

## 6. Acceptance criteria

1. A Joomla 5 and a Joomla 6 site is **detected** from its files, with the version; a Joomla 4, a WordPress and an empty directory are not.
2. The database access is read from `configuration.php` **without the file being run**; a socket, `pgsql` and an unreadable file are reported with what to do; no password appears in a log, a report, the manifest, the web interface or the command line.
3. A backup **leaves out** the caches, `tmp`, logs, sessions, the search index and the archives of other backup extensions, and keeps the empty directories; the manifest names the version, prefix, extensions and the address candidates.
4. A restore **on another domain, in a sub-directory, with another database and another prefix** gives a site whose front page and administration work, whose content has no trace of the old address (the foreign domain and the e-mail address untouched), whose `secret` is unchanged and whose `.htaccess` and absolute paths are right; the self-test says ok.
5. The same holds through the **`restore.php` wizard under 5 s and 64 MB** and after a **disaster recovery** onto an empty host, on MariaDB 10.11, MySQL 8.4 and MariaDB 11.8 (and a MySQL 8 backup onto MariaDB is refused as everywhere).
6. A restore that cannot succeed says so **before anything is written** (Joomla version unsupported, PHP or database server of the target too old, a prefix that does not match the tables).
7. `composer check` and the CI are green; the unit tests need no database; `docs/JOOMLA.md` is true.

## 7. Risks and decisions

### 7.1 Risks

1. **The old address is not stored anywhere.** The detection by frequency in the content can propose a wrong host (a CDN, a social network). Mitigation: it is a proposal, shown with the other candidates and the counts, replaced only when the owner confirms it.
2. **A custom or very old `configuration.php`** (constants, computed values, an include). The reader reports what it does not understand; the profile can name the database by hand, as for any type.
3. **Extensions that keep the address in files or in their own tables in forms the generic replacement cannot know** (page builders with their own serialization, SEF extensions with large URL tables, caches in the database). Known, out of scope; the field test lists them; the "as built" of work package 4 says what was tested.
4. **Large tables of sessions, logs and the search index** make dumps slow and big; they are structure only by default. The numbers come from work package 1.
5. **Database sockets** (`localhost:/path`) are common on shared hosts. `DatabaseSettings` knows host and port only. If the field test shows that sockets matter, a socket field is added to `DatabaseSettings` (a change of the core and of the profile format, so it is not part of this plan).
6. **MySQL 8 collations onto MariaDB** (`utf8mb4_0900_ai_ci`): the known gap of the restore; Joomla 5 and 6 use `utf8mb4`, so it hits Joomla sites as much as PrestaShop sites.
7. **Joomla's own behaviour after a move** that the plan does not foresee (a stored absolute path in a table, a cached URL). The spikes of work package 1 move a copy without adaptation to see what breaks.
8. **`.htaccess` in a sub-directory.** The rules of `htaccess.txt` that Joomla ships anchor the API at the root (`RewriteCond %{REQUEST_URI} ^/api/`); in a sub-directory `RewriteBase` alone does not move them. Work package 4 builds the rewrite on a real site in a sub-directory and says what it changes besides `RewriteBase`.

## 8. Findings of work package 1 (spikes)

The spike (`tools/spikes/joomla/`, 2026-10-23): the images `joomla:5.4-php8.3-apache` (Joomla **5.4.8**) and `joomla:6-php8.4-apache` (Joomla **6.2.0**), each installed by the image's own installer into a database of its own on the stack's MariaDB 10.11 (`up.sh`), then looked at and spoilt on purpose (`experiments.sh`, `livesite.sh`, `dbtype.sh`; `probe.php` asks the front page, the administrator login and the API).

1. **The images and the installer.** There is **no PHP 8.4 image of Joomla 5** (`5-php8.3-apache`, `5.4-php8.3-apache`; the tags with `php8.4` exist for 6). The installer of the image runs by itself when the variables `JOOMLA_DB_HOST`, `JOOMLA_DB_USER`, `JOOMLA_DB_PASSWORD`, `JOOMLA_DB_NAME`, `JOOMLA_SITE_NAME` and `JOOMLA_ADMIN_USER`/`_USERNAME`/`_PASSWORD`/`_EMAIL` are set; after about a minute the `installation` directory is gone and `configuration.php` exists. A fresh site has **about 9,550 to 9,850 files in 3,470 directories (117 to 120 MB, `media` 44 MB, `libraries` 36 MB), no symbolic links**, files mode 644, directories 755, and 76 tables of 4.5 MB (a dump of 360 KB). The tables are `utf8mb4_unicode_ci`; 74 are InnoDB and `finder_tokens` and `finder_tokens_aggregate` use the **MEMORY** engine.
2. **Version.** `libraries/src/Version.php` has `public const MAJOR_VERSION`, `MINOR_VERSION`, `PATCH_VERSION` and `EXTRA_VERSION` as plain constants (5, 4, 8, '' and 6, 2, 0, ''): a tokenizer reads them without running the file. `libraries/vendor/composer/platform_check.php` gives the PHP minimum: **8.1** (80100) for 5.4 and **8.3** (80300) for 6.2.
3. **`configuration.php`.** Class `JConfig`, one `public $name = value;` per line, **tab indentation, line feeds**, values as single-quoted strings, integers, `true`/`false` and `0`/`1`. **The same 67 properties in 5.4 and 6.2.** The database: `dbtype` (`'mysqli'`), `host` (`'db'`: **plain, no port property**), `user`, `password`, `db`, `dbprefix` (**random with an underscore**, `'joom_'` here), `dbencryption`, `dbsslverifyservercert`, `dbsslkey`, `dbsslcert`, `dbsslca`, `dbsslcipher`. Also `live_site` (empty), `secret` (16 characters), `smtppass`, `smtpuser`, `sef`, `sef_rewrite` (false), `offline` (false), `mailonline` (true), `robots` (empty), `session_handler` (`'database'`), `cache_handler` (`'file'`), `caching` (0), `offset`, `log_path` (`'/var/www/html/administrator/logs'`) and `tmp_path` (`'/var/www/html/tmp'`). There is **no `cache_path`, no `dbport`, no `cookie_domain`** in these two versions. **The file has mode 0444 and belongs to the web server's user**: a restore that wants to rewrite it must make it writable first (the owner can; another user cannot). The values of the two files are in `tests/fixtures/joomla/` with test values.
4. **Directories.** `cache`, `administrator/cache`, `administrator/logs` and `tmp` hold only an `index.html` placeholder in a fresh site; there is **no `logs` directory and no `.htaccess`**, only `htaccess.txt` and `web.config.txt`. `htaccess.txt` has `# RewriteBase /` commented out (line 96) and rules that anchor at the root: `RewriteCond %{REQUEST_URI} ^/api/` and `!^/index\.php` (risk 8).
5. **What breaks, and what does not** (`experiments.sh`; "ok" = front page 200, administrator login 200):
   - `tmp` missing: **ok**. `cache` and `administrator/cache` missing: **ok** (Joomla makes `administrator/cache` again at the first request, not `cache`). `log_path` and `tmp_path` pointing to directories that do not exist: **ok** for the pages (what writes there fails quietly). So the directories can be left out of a backup, and the paths in `configuration.php` do not break the pages, but a restore makes both right.
   - **`live_site` set to another address breaks the site**: the front page answers `301` with a `Location` of the request's own address (a redirect loop for a browser), in both versions and with or without a path (`https://moved.example/sub` also gives a 404 on the login page); the administrator keeps working. So a restore **must** rewrite or clear it (3.5 step 2).
   - `session`, `finder_links`, `finder_links_terms`, `finder_terms`, `finder_tokens`, `finder_tokens_aggregate`, `finder_taxonomy_map`, `finder_logging`, `action_logs` and `updates` emptied: **ok**, and `php cli/joomla.php finder:index` fills the index again. **Emptying `finder_taxonomy` as well is not ok**: its single ROOT row (`id 1`, `parent_id 0`, title `ROOT`) is needed, and the indexer stops with `MapTable::_getNode(1, id) failed`; put back, the indexer runs. `finder_types` is made again by the indexer's set-up but is kept anyway.
   - **`dbtype` `pdomysql` works** in 5.4 and 6.2 (the front page answers 200).
6. **The target's PHP.** The PrestaShop image that is the stack's target (PHP 8.4.15) has `pdo_mysql` and **no `mysqli`** (and no `imagick`, no `exif`); Joomla's installer checks `json`, `zlib`, `xml`, `mbstring` (errors) and `gd`, `iconv`, `zip`, `intl` (`transliterator_transliterate`) (warnings) and needs a database driver. All of those except `mysqli` are there. A restored Joomla whose `configuration.php` says `mysqli` would not start on that host without the change of `dbtype`: the restore does it (3.5 step 2).
7. **A fresh database holds no absolute URL at all** (not even the help URL, which is in `configuration.php`). The address of a site is in what its owner made: so the seed of work package 5 creates the content (articles, custom modules, menu items of the type URL, template parameters, redirects), and the candidates of 3.4 are worth only as much as that content.
8. **Table names** (`#__` = the prefix): sessions `session`, remember-me tokens `user_keys`, `updates`, `update_sites`, `update_sites_extensions`, `action_logs`, `action_logs_users`, `action_logs_extensions`, `action_log_config`, `scheduler_tasks`, `scheduler_logs`, `postinstall_messages`, `mail_templates`, and the Smart Search tables `finder_filters`, `finder_links`, `finder_links_terms`, `finder_logging`, `finder_taxonomy`, `finder_taxonomy_map`, `finder_terms`, `finder_terms_common` (174 rows of stop words), `finder_tokens`, `finder_tokens_aggregate`, `finder_types`. There are **no `finder_links_terms0` ... `f`** (those were Joomla 3). `#__extensions` has 251 rows in 5.4 and 6.2 (components 36, plugins 156, modules 49, templates 3, languages 3, libraries 2, a package and a file), `protected` marks the core ones.
9. **The pages the self-test can ask** answer as expected: `/` is 200 with `<meta name="generator" content="Joomla! - Open Source Content Management">` (on by default) and the title of the home page, `/administrator/` is 200 with the login form; `/api/index.php/v1/content/articles` is 406 without an `Accept` header (not used).

**Consequences for the plan, already made above:** Joomla 4 out (the owner's decision); the filter list of 3.3 exactly (and `finder_taxonomy` never structure only); `EnsureSkeleton` in step 5; `dbtype` and the stale `live_site` in step 2; the extension checks of `restoreChecks`; the images and the installer in 4.2; risk 8.

## 9. As built

### Work package 1: the spikes

**Done 2026-10-23.** *What exists:* `tools/spikes/joomla/` (`up.sh` and `down.sh` start and remove the two installations on the stack's `db`; `experiments.sh`, `livesite.sh`, `dbtype.sh` and `probe.php` are what section 8 was read with) and `tests/fixtures/joomla/` (the two `configuration.php` files with test values and a README). *Where it differs from the plan:* the corrections listed at the end of section 8 (Joomla 4 dropped, the filters, `EnsureSkeleton`, `dbtype`, `live_site`). *What is known to be missing:* the database server minimum of Joomla 6 (MariaDB 10.4, MySQL 8.0.13 from secondary sources) was not found in the code, the spike ran on MariaDB 10.11 only (the other two servers come with work package 5), and a real move into a sub-directory (the `.htaccess` question of risk 8) waits for work package 4.

### Work package 2: the configuration reader and writer

**Done 2026-10-23.** *What exists:* `plugins/joomla/src/Config/` - `JoomlaConfigFile` (the immutable reader and writer: `fromString`, `fromPath`, `all`, `get`, `has`, `notUnderstood`, `database()`, `with`, `withMany`, `withDatabase`, `writeTo`, `splitHost`), `JoomlaConfigParser` (the tokenizer: `public $name = <literal>;` inside `class JConfig`), `ConfigEntry`, `ParsedConfig`, and `Exception/InvalidConfigFile`; the namespace `ThreadSafe\Joomla\` in the autoload of `composer.json`; `tests/Unit/Joomla/JoomlaConfigFileTest.php` (43 tests, among them the two real files of 5.4 and 6.2, the proof that nothing in the file runs, and 300 random strings written and read back). *Where it differs from the plan:* one class is reader and writer (as `ParametersFile` of PrestaShop), not two; the files of Joomla have **67** properties (the count of 66 in the first findings was one short); no `chmod` is needed for mode 0444 because the file is replaced, not opened (`AtomicFile`); the PHP interface of the profile is always `auto` (`dbtype` says what Joomla uses, not what ThreadSafe needs), and `withDatabase` writes `dbtype` only when the restore gives one. A value with a NUL byte cannot be written (`var_export` would make a concatenation of it). *What is known to be missing:* a `host` that is a socket or `p:name` is refused with a message and not supported (risk 5); properties of the site's own with expressions as values are left alone and listed by `notUnderstood()`, which the type reports at "Look at the site" in work package 3.

### Work package 3: the plugin, the backup side

**Done 2026-10-23.** *What exists:* `plugins/joomla/` - `plugin.json` (id `joomla`, title "Joomla"), `resources/backup-defaults.json` (3.3 exactly), `src/JoomlaType.php` (the entry class: `WebsiteType` and `Backupable`), `src/Installation.php` (the version from `libraries/src/Version.php` by regular expression, never included; `isInstalled`), `src/Backup/JoomlaBackup.php` (`detect`: Joomla 5 and 6 with a `configuration.php` and an `administrator` folder, the version with a pre-release suffix; `databaseSettings`; `defaultFilters`; `manifestExtras`), `src/Backup/AddressCandidates.php` (the hosts of the absolute URLs in the content, counted, in plain text and JSON, a bounded sample read row by row), `src/RequestBuilder.php` and `src/Steps/NotYetBuilt.php` (the migration side, see below). The type is in the type lists of `profile add`, the profile form ("Look at the site") and `migrate`. Tests: `tests/Unit/Joomla/` (`JoomlaBackupTest`, `AddressCandidatesTest`, `JoomlaTypeTest`) and `tests/Support/FakeConnection` (a `Connection` that answers from canned rows, for code that only reads). *Where it differs from the plan:* the facts of the configuration file (site name, `dbType`, `dbPrefix`, `liveSite`, `offline`, `sef`, `sefRewrite`, the properties that are not literals) are collected by `detect()` into the `details` of the detected site, because `manifestExtras()` gets no path; the extensions listed in the manifest are those whose `manifest_cache` author is not "Joomla! Project" (the core ones are counted: **verify** on a real site in work package 5); `migrate joomla` is registered but **refuses** (one step, `NotYetBuilt`, throws `GuardFailed`: exit code 2) and there is no `Restorable`, so a restore of a Joomla backup says that the type does not support restores, until work package 4. *What is known to be missing:* the manifest extras were tested against a fake connection only (the real server comes with work package 5); the address candidates read at most 500 rows of 20,000 bytes per column, a sample, not a census.

### Work package 4: the restore side and the migration

**Built 2026-10-24; the proof on a real Joomla is work package 5.** *What exists:* `JoomlaType` is now also `Restorable` and has the steps (the placeholder step is gone): `ReadJoomlaState` (guards: a Joomla 5 or 6, a `configuration.php`, a database that opens and has `<prefix>extensions`; a warning if the server is below Joomla 6's minimum; findings as plain data for a run in ticks), `EnsureSkeleton` (`tmp`, `cache`, `administrator/cache`, `administrator/logs`, each with Joomla's own placeholder `<!DOCTYPE html><title></title>`), `WriteConfiguration` (the database, `dbtype` by the extensions this PHP has, `log_path`, `tmp_path`, `live_site`; replaces the file, so mode 0444 is kept), the **generic** `ReplaceContentDomains` (the Joomla type builds on the generic one, as the concept says; `State::store` hands it the connection), `RewriteHtaccess` with `HtaccessRewriter` (`RewriteBase` and the three root-anchored conditions of the API, shown to round-trip on Joomla's own `htaccess.txt`), `DiscardCaches` (the cache directories, `session`, `updates`) and `SelfTest` (front page and `/administrator/`). `Restore\JoomlaRestore` (fields `from`, `to`, `path`; the old address from `live_site`, else the most frequent host; checks), `RequestBuilder` (the option `path`, the tables that the content replacement skips), the option `--path` of `migrate joomla`, `docs/MIGRATE.md` section 13.
