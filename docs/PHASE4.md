## 1. Goal and scope

Today everything is done on the command line (`profile`, `backup`, `backups`, `verify`, `restore`). Phase 4 gives the person who has no shell, or does not want one, the same abilities in a browser: see all sites and the state of their backups at a glance, create and change site profiles, start a backup and watch it, check, download and delete backups, and get the tools to restore one. **It adds no new engine:** the web interface calls the same classes as the command line (section 3.3), and everything it does can still be done with the CLI.

| In scope | Out of scope (later phases) |
|---|---|
| login of one administrator, brute-force protection, CSRF, CSP, audit log, the interface can be switched off | several users and roles (the data model leaves room, section 3.2) |
| dashboard: one card per profile with last backup, status, warnings, running job; header totals | schedule, "next run", heartbeat of the trigger, retention, storage cap (phase 5; the places in the UI are left out, not drawn empty) |
| profile management: list, create (detect the application, propose the filters, connection test), edit, delete | remote storage (SFTP, S3, WebDAV) and the `transfers[]` columns |
| manual backup as ticks driven by the browser: start, progress, continue after the tab was closed, abandon, one run at a time | backups started by a cron trigger, run in a CLI process (phase 5; the dashboard must show and continue such runs, section 3.4) |
| backup overview per profile: list from the sidecars, details, **verify** (SHA-256 and ZIP structure, as ticks), delete | encryption of archives and the key handling (phase 5) |
| **download** with Range/resume, single-file and multi-part, warning above a threshold with path, command and SHA-256 | anonymisation of staging copies |
| "restore help": build and download `restore.php` and a fresh `restore-key.php`, instructions for the chosen backup | a restore started from inside the interface (the restore tool stays a separate, deletable single file, [PHASE3.md](PHASE3.md) 3.1) |
| an installation check ("security panel"): data folder and storage reachable from outside, HTTPS, PHP CLI binary found | automatic updates of ThreadSafe |

Phase 4 ends with the **browser walk-through** (section 6, criterion 1): in a real browser, log in, create the profile of the seeded Docker shop, run a backup under low PHP limits, verify it, download it in two parts with a broken connection in between, delete it – and the same backup restores through `restore.php`.

## 2. Deliverables

1. `src/Web/` grows from the wizard classes to an application: kernel/router, authentication, views, the pages of section 3.5; `public/index.php` as the only entry point.
2. Services shared with the CLI (`src/App`, section 3.3): the commands `profile`, `backup`, `backups`, `verify` are refactored onto them without a change of behaviour.
3. `threadsafe admin` (set or change the administrator password, switch the interface on or off) and a web setup for hosts without a usable shell.
4. `VerifyRun` (a ticked task, because a SHA-256 over a multi-gigabyte archive does not fit into a request).
5. Download streaming with Range, tokens and the warning dialog.
6. Unit tests (router, authentication, throttle, CSRF, token, range parser, escaping), integration tests in Docker through HTTP (the journeys of section 4), a browser walk-through, `docs/WEB.md` (installing and using the interface).

## 3. Design

### 3.1 Installation and entry point

ThreadSafe is installed as a directory (`git clone` or an archive, `composer install --no-dev` – no other dependency may appear at run time). The web server's document root should be `public/`; that directory contains only `index.php` and the static files (`app.css`, `app.js`), so `src/`, `data/`, `plugins/` and `vendor/` are never served. On shared hosting where the document root cannot be changed, the whole directory sits inside the web root and a `.htaccess` in every directory except `public/` denies access (the same technique as `StateDirectory`); the installation check (3.9) reports whether that holds, because it differs per web server and nothing here can be assumed.

- **`data/`** (profiles, runs, locks, sessions, audit log, administrator file, configuration): 0700, 0600 files, outside the web root where possible; the location is `THREADSAFE_DATA` or `data/` (as today). It already holds the database passwords of `generic` profiles, so it is as sensitive as the storage of the backups.
- **Storage of a profile** is the directory the profile names (as today); the interface never serves it directly – only `download` (3.6) reads from it.
- The interface does **not** exist until it is switched on: the default configuration has `web.enabled = false`. `threadsafe admin enable` (or the web setup, 3.2) turns it on; with it off `public/index.php` answers 404 and nothing else. Reason: CONCEPT 6 says "primarily operated via CLI; the UI can be switched off", and a tool that can read every site on the server should not be exposed by an unpacked archive.

### 3.2 Authentication and sessions

- **One administrator, one password**, stored in `data/admin.json` (mode 0600) as `password_hash(..., PASSWORD_ARGON2ID)`; hosts whose PHP lacks Argon2id fall back to bcrypt, and the file says which (Argon2id costs about 0.2 s per login and works under a 16 MB `memory_limit`, finding 3; the live host still has to be asked, `tools/spikes/host-probe.php` now does). The file has a `users` list with one entry so that roles can be added without a format change; the code only knows one.
- **Setting the password:** `threadsafe admin password` reads the new password from a prompt, `--password-file=FILE` or `THREADSAFE_ADMIN_PASSWORD` (never a command line option, AGENTS rule). Where there is no usable shell, the **web setup** works like the restore wizard: it is reachable only while `data/admin.json` does not exist **and** a key file `data/setup-key.php` (`<?php return 'secret';`, put there by the person, deleted by the setup) matches. Without the key file the page shows what to do, and nothing else.
- **Login:** the throttle of `AccessKey` (3 free failures, then 5 s doubling to 5 min, kept in a file, log of failures with address) is generalised into a `Throttle` that both use. A constant-time comparison, the same message for "no such user" and "wrong password", `password_needs_rehash` on success.
- **Sessions:** `Sessions` (hash-named files, 0600, idle timeout 2 h; absolute lifetime 12 h) moves from the wizard's state directory to `data/sessions/`; cookie `HttpOnly`, `SameSite=Strict`, `Secure` when the request is HTTPS; the session id is renewed on login; logout deletes the file. The plain-HTTP warning of the wizard (login over HTTP shows a confirmation) is kept.
- **CSRF:** a token per session in every form and in the header of every script request; every state-changing request is `POST` (nothing changes on `GET`, also not logout and not delete); `Origin`/`Referer` are checked when present.
- **CSP and headers:** `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; connect-src 'self'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'` (`connect-src` is needed by the tick requests and the data probe of 3.9, finding 6), `X-Content-Type-Options`, `Referrer-Policy: same-origin`, `Cache-Control: no-store` on every page. No inline script or style, so no nonce is needed: the script is the static `app.js`.
- **Audit log:** `data/audit.log` (one JSON line each): login success/failure, logout, profile created/changed/removed, backup started/finished/abandoned, verify, download started/finished, delete, password change, settings change; no passwords, no file contents. Rotated at a size (default 5 MB, three files). The interface shows the last entries.

**As built (work package 2).** The application lives in **`src/Admin/`** (namespace `ThreadSafe\Admin`), not in `src/Web/`, and **`RestoreBuilder` leaves `src/Admin/` out of `restore.php`** (a test checks it); what both share stays in `src/Web/`: `Request` (now with headers), `Response`, `Html`, `Sessions` (now with an idle time and an absolute lifetime of its own) and `Throttle`, which `AccessKey` now uses (its behaviour and tests are unchanged). Files: `Kernel` (request → response, the three states below, security headers, CSRF and origin checks, session saving), `Router` (patterns with `{id}`, `{name}`, `{hex}` placeholders that accept nothing else; a known path with another method is 405), `Urls` (routes as paths, or `index.php?route=...` with `web.prettyUrls = false`), `Context`, `View` (the frame of every page; no inline script or style, the CSRF token in a `<meta>`), `AuthController` (login, logout, setup), `DashboardController` (profile count and recent audit entries only), `Config`, `AdminStore`, `AuditLog`, `Csrf`, `Services`, `Entry`; `public/index.php`, `public/app.css`, `public/app.js`, `public/.htaccess` (rewrite to `index.php`, directory open) and a root `.htaccess` that closes everything else when the whole tree lies below a web root; `threadsafe admin password|enable|disable|status`.

Where it differs from the plan above: (1) **three states instead of "off unless enabled":** *off* (no administrator and no setup key, or `web.enabled` false): every address is a plain 404 and **nothing is written, not even the data directory**; *setup* (no administrator and `data/setup-key.php` exists – this works while the interface is still "off", because putting the key file there is the decision to switch it on): only `/setup`, everything else redirects to it; *on*: login and the pages behind it (with `web.enabled` true and nothing else, a page says how to set a password). A finished setup sets the password, sets `web.enabled`, deletes the key file. (2) The login throttle is global like the key's (3 free failures, then 5 s doubling to 5 min; attempts during the wait are refused without being compared and not counted, so the wait of a long attack stays at the wait of three failures). (3) The login form has a user field (default user `admin`); passwords need 10 characters (bcrypt: at most 72 bytes). (4) Static files are `public/app.css` and `public/app.js`, not `/assets/`. (5) The Origin/Referer check applies to every POST, the token to every POST behind the login (the login and setup forms have no session yet; `SameSite=Strict` and the origin check protect them). (6) An unknown address without a session redirects to the login instead of showing a 404, so nothing behind the login is revealed. (7) `AuditLog` drops any context key that sounds like a secret (`pass`, `secret`, `key`, `token`, `hash`, `cookie`) and everything that is not a single value.

Proof: 66 new unit tests (`tests/Unit/Admin/*`, `Web/ThrottleTest`, `Cli/AdminCommandTest`; the whole suite and the bundle run pass, PHPStan level 8) and a smoke test through Apache with the whole tree below a web root (the Docker target, removed afterwards): off by default → 404 everywhere; `data/`, `src/`, `vendor/`, `bin/`, `plugins/`, `composer.json` and the `.htaccess` files → 403; `app.css`/`app.js` → 200; setup with the key file, login, dashboard, logout in the built-in browser (375 px and dark: no horizontal scroll, dark colours applied, no CSP violation; the screenshots of the pane timed out, so the layout was checked through computed styles only). **Not done yet:** the settings and audit pages (work package 7), the Docker `web` service and HTTP integration tests (work package 8); the password prompt of `admin password` needs a terminal and is not covered by a test (file and environment are).

### 3.3 One engine, two front ends (services)

The risk of a web interface is a second implementation of what the CLI does. The rule: **the pages contain no business logic.** What `BackupCommand`, `ProfileCommand`, `BackupsCommand` and `VerifyCommand` do between parsing options and printing text moves into services in `src/App`, and both front ends call them:

| Service | Does | Extracted from |
|---|---|---|
| `ProfileService` | list, load, create/update from a plain array (with the type's detection and proposed filters), test, remove; returns `TestReport` and validation errors per field | `ProfileCommand` (`fields`, `database`, `store`, `test`, `remove`) |
| `BackupService` | start a run (locks, space check, `force`, **refuse while a web run is active**, 3.4), execute one tick, resume, abandon, list unfinished runs, report the result | `BackupCommand` (`backup`, `resume`, `executor`, `execute`) |
| `CatalogService` | list backups, details, delete, rebuild a sidecar, verify (as a run) | `BackupsCommand`, `VerifyCommand` |
| `Overview` | the dashboard's data: per profile last backup, age, size, status, warnings, unfinished run | new (reads `BackupCatalog`, `RunStore`, `SpaceCheck`, `LocalStorage::isProtected`) |

The commands keep their output and exit codes; the existing CLI tests are the proof that the refactoring changes nothing. The pages then format the same service results as HTML, and a service returns plain data (arrays, the existing value objects) so that it is testable without HTTP.

### 3.4 Running a backup from the browser

A manual backup from the web interface is a **web task** (CONCEPT 5.6): PHP limits apply, every request does one tick, the database is dumped per table and the manifest says `consistency: table`.

- **Start** (`POST /profiles/<id>/backup`): the checks the CLI does (profile exists, no other run, space check with the `force` checkbox), then `Executor::start`, answer with the run page. **One run at a time, instance wide** (as the CLI's `backup.lock`), so a second start is refused with a link to the running one.
- **Tick** (`POST /runs/<id>/tick`, answered as JSON): `Executor::execute($id, maxTicks: 1)` with `Budget::forThisProcess()` (≈ 60 % of `max_execution_time`); the script calls it again at once until the run is done, shows the progress line and a bar from the state (files done of files found, tables done of tables), and never calls it more often than once per answer. The answer carries the same fields the restore wizard's tick does.
- **The lock must live shorter than a process.** The CLI holds `backup.lock` with `flock` for the lifetime of the process; a web run spans many processes. So the **run's own lock** (`RunStore::lockPath`) is taken, non-blocking, **per tick**: a second browser tab that ticks the same run at the same moment gets "busy, try again" and waits, never a second writer into the same archive. The engine's `RunStore::isInterrupted` (status `running` and no lock held) is **not usable as it is**: between two ticks no process holds the lock, so a live web run looks interrupted all the time (finding 2). A run is therefore *active* when its lock is held **or** its status is `running` and `updated` is newer than a limit (default three times the tick budget, at least 60 s), and *interrupted* otherwise. A new run is refused while another is active; an interrupted one is shown with **Continue** and **Abandon** (`BackupRun::abandon` cleans up its files). **The same rule must be applied by the CLI's `backup`:** its instance-wide lock (`backup.lock`) is held for the life of the CLI process and is free between web ticks, so without the check a CLI backup could run next to a web backup (finding 2); `BackupService` does the check for both.
- **Closing the tab** does not stop anything that matters: the next tick simply does not come, the run becomes *interrupted* after the limit, and it is continued from its saved state by **Continue**, by a later `threadsafe backup --resume=…`, or (phase 5) by the cron trigger. The dashboard shows an active or interrupted run on its card.
- **Result:** the finished run's result (archive names, size, files, tables, rows, warnings) is shown on the run page and kept in the backup's sidecar as today; the run file is deleted as the CLI does.
- **Failure:** the message of the engine is shown unchanged, with the same advice the CLI prints; the files of the failed run are removed (`abandon`), its state is kept for diagnosis like in the CLI.

**As built (work package 4).** `src/App/BackupService` (used by the pages and, for the one-at-a-time rule, by `backup` and `backups --discard-run`) does: `startWeb`, `tick` (one tick under the run's own lock; a tick that fails removes what the run wrote and keeps the record as failed), `abandon`, `dismiss`, `state`/`activeRun`/`assertNoActiveRun`, `progress`, `result`, `prune` (records of finished runs go after a day, failed ones after a week). **The active rule of the plan is implemented as found in spike 1b:** a run is *active* when its lock is held, or when it is a **web run** (new field `BackupState::$web`, set by `startWeb`; old states read as command line runs) and its last tick is younger than the grace (the larger of 60 s and 1.8 times `max_execution_time`); otherwise a running run is *interrupted*. A command line run is judged by its lock alone, so a `backup` right after a killed command line process is not blocked (a test checks it), while a `backup` next to an active web run is refused with "One backup at a time" and `backup --resume` / `backups --discard-run` of an active run are refused. `EngineException::BUSY` marks the refusal of a run that another process is ticking, so the page can answer "busy" instead of "failed". `BackupProgress` reads a percentage from the saved state (none while the site is listed; the dump counts tables, the packing counts the read part of the file list).

The pages (`BackupController`): `POST /profiles/{id}/backup` (with a "too little room" override), `GET /runs/{run}`, `POST /runs/{run}/tick` (JSON: `running` with percent and label, `busy`, `finished`, `failed` with the reason, `missing`; a login that has ended answers 401 `login`), `POST /runs/{run}/continue` (one tick for a browser without script, then back to the run page), `POST /runs/{run}/abandon`, `POST /runs/{run}/dismiss`. The run page shows a `<progress>` (no style attribute: the policy forbids it), the label of the engine, "Do the next step" (hidden by script) and "Cancel the backup"; `app.js` asks for ticks one after the other (100 ms between them; 1.5 s after "busy"; retries with a growing delay and a note after a lost connection, giving up after 20), reloads when the run ends, and says so when the session has ended. An interrupted run shows "Continue" and "Give it up"; a failed one shows the reason and "Dismiss". The profile page has "Back up now" and the runs of that profile; the dashboard lists all runs that are going, interrupted or failed (and finished ones for an hour). Every start, end, failure and giving up is in the audit log.

Where it differs from the plan: (1) **giving up** is allowed whenever no process holds the run's lock - also for a web run whose last tick was a moment ago, which is how a person cancels; a run in the middle of a tick answers "try again in a moment"; (2) the instance-wide lock `backup.lock` of the command line is **not** taken by the web (nothing could hold it between ticks); the rule above replaces it for both sides; (3) the "Continue" of an interrupted run needs a click (a page does not tick an interrupted run by itself), because someone else may be looking at it too.

Proof: 26 new unit tests (`Unit/App/BackupServiceTest`, `Unit/Admin/BackupPagesTest`; the existing backup tests unchanged; suite 2357 tests, PHPStan level 8, bundle run) and a run in the built-in browser against the Docker target (Apache `mod_php`, `max_execution_time` 6 s and 64 MB through `.htaccess`, so ticks of 3.6 s; a PrestaShop clone of 673 MB / 46,840 entries and 299 tables): a backup took 5 ticks and 17 s and the script followed it to the result page (300 MB, `unzip -t` clean, `threadsafe verify` intact); a second start while one was active was refused with the message and led to the running one; a run left alone after two ticks became **interrupted after 60 s**, was continued with one click and finished; all three archives have the same entry count (46,840) and uncompressed size (648,462,182 bytes). Not covered: two browsers ticking truly in parallel against a real web server (the lock is tested with two processes in the spike and with a held lock here), a very large site that needs hundreds of ticks, and the live host.

### 3.6 Download and large archives

CONCEPT 5.4 describes the technique; this section fixes the details.

- **Token, not path.** `GET …/download` (a page, no bytes) shows the dialog; its button posts and receives a **token** (random, 32 bytes) that is stored in the session, bound to *profile + backup + part*, valid for 2 hours or until logout. `GET /download/<token>/<part>` streams the file. CONCEPT says "single-use"; a single-use token cannot work together with **Range**, because a resumed download is a second request. So the token is valid for repeated requests *of that one file in that one session*, and each use is written to the audit log (decision 7).
- **Streaming:** `Content-Length`, `Accept-Ranges: bytes`, `Content-Disposition: attachment` with the archive's own name, `Content-Type: application/zip`, `ETag` (the SHA-256 from the sidecar) and `If-Range`; single ranges (`bytes=a-b`, `a-`, `-n`; multiple ranges answer with the whole file); 206/416 handled; 1 MB blocks with `fread`/`echo`/`flush`, output buffering and compression switched off (`ini_set('zlib.output_compression', '0')`, `apache_setenv('no-gzip', '1')`), `set_time_limit(0)` (a safety only: on Linux `max_execution_time` counts CPU time, finding 1), `ignore_user_abort(true)` **together with `connection_aborted()` checked after every block** (the script must stop reading when the client is gone, finding 1) and the session lock released before the first byte (so other pages work while a download runs).
- **`X-Sendfile` / `X-Accel-Redirect`:** off by default; `download.accel = sendfile|nginx` in the configuration, with the internal location the person set up. The installation check cannot detect whether the web server honours the header; the documentation says how to test it with a small file.
- **The warning:** above `download.warnAbove` (default 500 MB) the dialog says that large downloads can fail (PHP and web server time limits, proxies and CDNs, the browser), recommends server access, and shows the **absolute path**, an `scp` and an `rsync` example with placeholders (never a guessed user or host), and the **SHA-256** of each part to compare afterwards. The download button is still there.
- **Multi-part backups** list their parts with size and SHA-256 each; every part is its own download.
- **Never from the storage directly:** `GET /download/<token>/<part>` resolves `part` through the catalog (`BackupCatalog::archiveParts`), not from a path in the request.
- **Not in the first version:** compression of the download (the archive is compressed), a streamed re-zip of all parts, bandwidth limits.

**As built (work package 6).** `Admin/DownloadController` (the dialog, the token, the file), `Admin/Download` (sends a file) and `Admin/ByteRange` (the `Range` header). The page `GET /profiles/{id}/backups/{name}/download` lists every part with its size and SHA-256 and a button each; above `download.warnAbove` (default 500 MB; the smallest setting is 1 MiB) it adds the warning of 3.6 with the **absolute path**, an `scp` and an `rsync` example with `USER@HOST` as placeholders, and the hint to compare the checksum; the button stays. The button posts the part (`POST` on the same address, with the CSRF token); the controller checks that the name is a part named in the backup's record, makes a random **token** (24 bytes), keeps it in the session (`downloads`: profile, backup, part, expiry; at most 30, expired ones dropped) and redirects to `GET /download/{token}/{part}`. That address works for **two hours, for that part, in that session**, as often as needed (a resumed download is a second request), and dies with the logout; a token of another session, an expired one, one for another part, or a name that is not a part is a plain 404. The file is sent with `Content-Length`, `Accept-Ranges`, `ETag` (the part's SHA-256) **and `Last-Modified`**, one range (`206`/`416`), `If-Range` against either, blocks of 1 MB, `Cache-Control: private, no-transform` (not `no-store`, which would hinder a resume; `Kernel::secure` leaves a `Cache-Control` that the response has), and the loop stops when `connection_aborted()`. The sending is a **stream** on the response (`Response::$stream`, written when the response is sent), so the session is saved before the first byte; the audit log gets `download.start` and `download.end` (bytes sent, complete or not) and never the token. `download.accel` `sendfile` sends `X-Sendfile: <path>` and `nginx` sends `X-Accel-Redirect: <download.accelPrefix><path without the first slash>` (new setting `download.accelPrefix`, e.g. `/ts-files/` for `location /ts-files/ { internal; alias /; }`); then the web server does the ranges. Nothing but a part's own path is ever opened.

Where it differs from the plan: (1) the **ETag alone is not enough** - found against the Apache of the Docker target, whose PrestaShop `.htaccess` strips it from PHP responses; without a validator a browser cannot resume safely, so `Last-Modified` is sent and `If-Range` accepts the date as well; (2) the two web-server modes are implemented and unit-tested for their headers but **not tried against a web server that honours them**; (3) no "copy" button for the command (a later nicety).

Proof: 38 new unit tests (`Unit/Admin/DownloadTest`: the Range forms, 416, `If-Range` by ETag and by date, `HEAD`, the web-server headers, the report, hostile names, an empty file; `Unit/Admin/DownloadPagesTest`: the dialog and its warning, the token flow, a resumed download byte-equal to the file, a token per part, another session / after two hours / after logout, no name outside the record, the audit log without the token; suite 2424 tests, PHPStan level 8, the bundle run) and curl against the Docker target through Apache with `max_execution_time` 6 s: a 79 MB part in 0.4 s with the SHA-256 equal to the file's, 30 MB plus a `Range` for the rest joined to the same SHA-256, a client that leaves after 1 s noticed (`download.end` with 5 MB sent and `complete: false`), `If-Range` by date giving 206 and a wrong date 200, and a download throttled to 3 MB/s that took 26 s - four times the time limit - and still arrived complete. Not covered: a real browser's own resume (the Range behaviour is the standard one), the live host's FastCGI (spike 1a is still open there), and multi-gigabyte files.

### 3.7 Backup overview, verify, delete

The overview is read from the **sidecar files** (`BackupCatalog::entries`), never by opening ZIPs; a missing sidecar is rebuilt as `backups` does, with the cost of opening the archive once (the dashboard uses the cached list and does not rebuild; only the profile page does). Columns: date/time (UTC and the browser's local time through `<time datetime>`), kind (full / database only / files only), size and number of parts, duration, application version, status (**ok**, **unchecked**, **faulty**, **unknown**) and the verification date, actions **download**, **verify**, **details**, **delete**, **restore help**.

**Verify** reads every part (ZIP structure, CRC of every entry, SHA-256 of the part against the sidecar). That is as slow as reading the archive, so it runs as a task, `VerifyRun`, with the same tick/resume rules as every task: state = part index, byte offset and the running SHA-256 context (`serialize(hash_init('sha256'))`, base64 in the JSON state: 447 bytes, no loss of speed, finding 5), then the entry walk of `Verifier::full`. `threadsafe verify` keeps its behaviour and uses the same task with an unlimited budget. The result (status, date, findings) is written into the sidecar.

**Delete** needs a confirmation page that names what goes (backup, parts, sidecar) and a POST with CSRF; it removes the files through `LocalStorage::removeBackup` and writes the audit log. There is no "undo", the text says so. A backup that is being written (its run is active) cannot be deleted.

**As built (work package 5).** `Backup/VerifyRun` is the check as a task (`VerifyState` holds its state); `Verifier::verify` now runs the same task in one go with an unlimited budget, so **the command `verify` and the page share one implementation** and the 77 existing verification tests passed unchanged. The state is the stage (checksums, then archives), the part in work, the running SHA-256 (a serialised hash context, 447 bytes as measured), the position in the central directory of the archive being read (`entries($from, $position)`), the counts, the problems (at most 100 are kept, the rest is counted) - a test checks that the state stays under 20 KB and that many small ticks give exactly the report of one pass. An entry is read as a whole inside a tick; the overlap check needs the entries in file order, which every archive of ThreadSafe has (otherwise it is skipped for that part); `ZipReader::dataOffset` became public for it. `App/CatalogService` lists (from the sidecar files; a missing one is made again), finds, deletes (also all backups of a profile; refused while an active run is writing or checking that backup), and starts, ticks, discards and prunes checks (one check at a time; the rule for "active" is the one of the backup runs). `Admin/CatalogController` and its routes: the table on the profile page (made, size and parts, duration, application, state in words, actions), `GET /profiles/{id}/backups/{name}` (manifest: times, application and website type, tool and PHP version, counts, how the database was read, filters, parts with their SHA-256, shop addresses, warnings, objects that are not part of a backup), `POST .../verify`, `GET`/`POST .../delete` (a confirmation page; a POST with the token), and the check pages `GET /checks/{run}`, `POST /checks/{run}/tick|continue|discard`, which use the same script (`#run`, `data-tick-url`) as a backup run. **Removing a profile can now delete its backups too** (decision 11): a box on the confirmation page names their number and size; without it they stay. Audited: `backup.check`, `backup.checked` (with the result), `backup.deleted`, `profile.removed` with the number of backups deleted.

Where it differs from the plan: (1) **no "type" column** (full / database only / files only): the manifest does not record one, every backup is a full one; (2) **no date of the last check**: the sidecar keeps the result as the status only; a date needs a field in the sidecar (a later change of the format, not done here); (3) the check is "Check", the word "verify" stays in the command; (4) the backup overview is on the profile page, as planned, not a page of its own.

Proof: 29 new unit tests (`Unit/Backup/VerifyRunTest`, `Unit/App/CatalogServiceTest`, `Unit/Admin/CatalogPagesTest`; suite 2386 tests, PHPStan level 8, the bundle run), the backup integration tests (`BackupRunTest`, `BackupRoundTripTest`, `BackupResilienceTest`: they verify real backups) unchanged and green, and the Docker target through Apache with 2-6 s limits: a CLI backup of the 673 MB shop (4 parts of 100 MB) listed on the profile page, **checked in the browser: intact, 300 MB read**; after one byte of part 2 was flipped the check named the part (SHA-256 and the CRC32 of the entry), the list said FAULTY, the sidecar status was written; then the backup was deleted through the confirmation page and only the storage's protection files were left. A check of a 300 MB backup takes one tick of 3.6 s here; the ticks matter for archives of several gigabytes on a slower disk.

### 3.8 Restore help

For a chosen backup the page explains the restore in four steps (upload `restore.php` and `restore-key.php`, upload the backup parts, open `restore.php`, enter the key) and offers:

- **Download `restore.php`**: built on the fly from the installation's sources with `RestoreBuilder` (≈ 210 KB), cached in `data/cache/` under the program's version, or `dist/restore.php` if the installation ships it. A build takes about 1.0-1.4 s and 5.6 MB of PHP memory (finding 4), so it can run inside the request that asks for it; the cache saves the second build only.
- **Generate `restore-key.php`** with a random key, shown once on the page and downloadable as the file; the key is **not stored** on the server (it is a secret that belongs to the restore, not to the instance).
- the parts of the backup to upload, with their sizes and SHA-256, and the hints from [RESTORE.md](RESTORE.md): the target must be empty, the database must exist, PHP 8.4, `pdo_mysql` or `mysqli`.

**As built (work package 7).** *Dashboard:* `App/Overview` reads, for every profile, the sidecar files (`entries($id, false)`: nothing is made again, no archive opened unless a sidecar is missing), the run records, `stat`, the free space of the disk - never a database - and returns a card: the newest backup (time, age, size, state), the newest usable one, count and bytes, the run that is going / interrupted / failed, and the warnings with a level. The warnings are those of 3.9 that need no phase 5: no backup yet, no successful backup for more than `dashboard.warnAfterDays`, the newest backup faulty or incomplete, a failed run (with its reason) or an interrupted one, little free space (less than 1.2 times the last backup), storage not writable or without protection files, the site directory gone, storage unreadable. A card is **OK**, **Needs a look** or **Problem** - written on a badge, not only coloured - and has "Back up now" (or "Follow"/"Continue" while a run exists), "Backups", "Edit"; the header has the totals (sites, backups, bytes, running). *System page* (`SystemController`, `SystemChecks`): PHP and the length of a step, extensions (zlib, hash, json fail; mbstring, a database extension, `open_basedir` warn), the PHP command line binary, https, running as root, the data directory (writable, permissions, `.htaccess`, a left-over `setup-key.php`) and, per profile, the site directory, left-over `restore.php` / `restore-key.php` / `.threadsafe-restore` in it, and the storage (writable, protection files, free space). **"Can the data directory be fetched?"** is answered by the browser as measured in spike 1f: the page writes `data/probe.txt` and `app.js` asks for it at the two addresses where `data/` would be served if the program lay below the web root; the file coming back is reported as REACHABLE in red. The **settings form** edits idle minutes, plain addresses, the warning age, the download warning size and the web server mode (`download.accelPrefix` is new), and the audit log size; mistakes come back with what was typed, nothing is saved then, and a change is audited with the names of the keys. `web.enabled` is not on the form (switching the interface off from inside it would lock the person out). The **audit log** (50 entries) is on the page. *Restore help* (`RestoreController`, `RestoreKit`): `GET /profiles/{id}/backups/{name}/restore-help` with the four steps, the parts to upload with their SHA-256 and what the target needs (taken from the manifest: a database only if the backup has one, the space with 10 % to spare); `GET /restore-php` sends `restore.php` **built from this installation** (230 KB, cached in `data/cache/` per version and fingerprint of the sources, an older cache file is removed) through the same `Download` as the backups (Range, ETag), and `POST /restore-key` makes a new random key and sends `restore-key.php` as a file or shows the key once on the page; the key is stored nowhere, not even in the audit log.

Where it differs from the plan: (1) the settings page is part of the System page, not a page of its own; (2) the **"restore kit" is not one button** but the tool and the key separately, as the key must be new for every restore and the tool is the same; (3) the dashboard has **no "next run" and no heartbeat** (phase 5); (4) an audit key that sounds like a secret is dropped (found again here: a key named `keys` vanished, hence `changed`).

Proof: 26 new unit tests (`Unit/App/OverviewTest`, `Unit/Admin/SystemAndRestorePagesTest`; suite 2450 tests, PHPStan level 8, the bundle run) and the Docker target through Apache: the dashboard card of a fresh backup is OK with age "just now"; the System page's probe reports `/threadsafe-ui/data/probe.txt` as not reachable (HTTP 403) and its second address as "answers, but not with the probe file"; at 375 px the card fits (no horizontal scroll); `restore.php` is sent in 0.11 s the first time (built) and 7 ms the second (cached) and is byte-equal; **the downloaded tool restored a backup of a small site into an empty directory with `restore.php restore ... --yes` and the trees were equal**. Not covered yet: the full journey through the wizard with the kit from the page (work package 8), and the layout of the System page in a real screenshot (the pane could not draw one).

### 3.9 Installation check and dashboard warnings

A panel (`/system`, and a short list on the dashboard when something is wrong): PHP version and the extensions the engine needs; **is `data/` reachable from outside?** (the page writes `data/probe.txt` with a known content, then the script asks the browser for the URL where `data/` would be served; 200 with that content = exposed, 403/404 = not; a 404 counts only if the file was written; a loopback request from PHP is not reliable behind proxies; works under the CSP with `connect-src 'self'`, finding 6); is each storage directory protected (`LocalStorage::isProtected`) and writable, with free space; HTTPS in use; a PHP CLI binary found (`PhpBinary::cli()`) for `bin/threadsafe` and phase 5; file leftovers (`restore.php`, `restore-key.php`, `.threadsafe-restore/` in a site root, `setup-key.php`); the effective `max_execution_time` and `memory_limit` and the tick budget derived from them; whether the process runs as root or as a user other than the files' owner (CONCEPT 6 "foreign account").

Dashboard warnings per profile (CONCEPT 5.2, those that need no phase 5): no successful backup for *n* days (default 7; per instance), the last run failed, an interrupted run, little free space (`SpaceCheck` against the size of the last backup × 1.2), the storage is not writable or not protected, the site path no longer exists. The checks use only cheap reads (stat, sidecar list, `disk_free_space`); the database is touched only by an explicit **Test** button.

### 3.10 Configuration

`data/config.json` (0600, written by the settings page and `threadsafe admin`): `web.enabled`, `web.sessionIdleMinutes`, `download.warnAbove`, `download.accel`, `dashboard.warnAfterDays`, `audit.maxBytes`. Unknown keys are refused, as in profiles. Nothing in it is secret. The administrator's hash lives in its own file, so the configuration can be read and shown freely.

### 3.11 Views and design

Pages are produced by plain PHP functions over the existing `Html` helper – no template engine, no front-end build. `app.css` is one file (system font, a small set of colour tokens, light and dark by `prefers-color-scheme`, a layout that works at 375 px and 1280 px, visible focus, status never by colour alone); `app.js` is one file without a framework: the tick loop and progress bar, confirmation dialogs through `<dialog>`, copy-to-clipboard for the download dialog, local time formatting. Every page works without script except the progress of a running backup (the run page then shows a "Continue" button that does one tick per click). The language of the interface is English with all texts in one place per page so that a translation is possible later (decision 8).

## 4. Test strategy

### 4.1 Unit tests (no database, no network)

- **Router and kernel:** route table, method checks (`GET` never changes state), 404 for unknown ids and names that do not parse, error pages without stack traces.
- **Authentication:** hash and verify (Argon2id and the bcrypt fallback), rehash, throttle (counts, doubling, cap, reset on success; clock injected), constant time comparison used, setup only with the key file and only while no administrator exists, session idle and absolute timeout, id renewal, logout.
- **CSRF and headers:** missing, wrong and foreign-session token refused, `Origin` mismatch refused, CSP and the other headers on every response type, cookie attributes (`Secure` only on HTTPS).
- **Views:** escaping of every user-controlled field (profile name, note, paths, archive names, error messages) tested with `"><script>` and with control characters; no inline script or style anywhere (a test over the rendered pages); no password in any page, also not in the edit form.
- **Services:** `ProfileService` field validation and detection with a fake type, `BackupService` start/refuse/continue/abandon with a fake task, `Overview` warnings from fabricated catalogs.
- **Download:** the Range parser (all forms, overlaps, invalid, `If-Range`), token lifetime/binding/revocation, part resolution refuses names outside the catalog, the response headers; streaming to a memory stream in block-sized pieces.
- **`VerifyRun`:** resume at every tick boundary gives the same result as one pass; a flipped byte, a missing part and a wrong sidecar hash are found.
- **The CLI tests** of `profile`, `backup`, `backups`, `verify` stay unchanged and green after the refactoring (work package 3 and 4).

## 6. Acceptance criteria

1. **Browser walk-through:** in a real browser (375 px and desktop), log in, create the profile of the seeded shop, run a backup under `max_execution_time=5` / `memory_limit=64M`, verify it, download it (multi-part, with a broken connection in between, SHA-256 equal), delete it; no CSP violation, no console error.
2. **The same engine:** a backup made through the interface and one made by the CLI from the same state are equal in content (files, tables, manifest apart from time, consistency and ids); the CLI tests of the four refactored commands pass unchanged.
3. **Restore:** the `restore.php` and key generated by the interface restore a backup made by the interface (disaster recovery on the Docker stack, as in phase 3).
4. **Running backups:** a closed tab leaves an interrupted run that **Continue** and `backup --resume` both finish; two simultaneous ticks never corrupt an archive; a second backup is refused while one is active.
5. **Download:** Range and resume work; a backup larger than the threshold shows the warning with path, command and SHA-256; a part can only be fetched through a valid token of the same session.
6. **Security:** nothing is reachable without login except the login page (and the setup page while no administrator exists, with the key file); every state change needs a CSRF token; brute force is throttled; the secrets (passwords, the setup and restore keys, the administrator hash) appear in no page, log, audit entry or error message; `data/`, `src/`, `vendor/` and every storage directory are not served by URL.
7. **Switched off:** with `web.enabled = false` the entry point answers 404 and nothing else; the CLI is not affected.
8. **Multi-site:** ten profiles on the dashboard render without opening an archive and without touching a database (measured by the number of file and DB operations in a test).
9. Unit tests, PHPStan level 8 and the integration tests (`tests/stack/matrix.sh`) pass on MariaDB 10.11, MySQL 8.4 and MariaDB 11.8, and `composer test:bundle` still passes (the restore bundle is not affected by the new code).

## 7. Risks and decisions

**Risks**

- **A tool that reads every site on the server, on the internet.** CONCEPT 6 names it. Mitigation: off by default, document root on `public/`, `.htaccess` fallback, an installation check that says what is exposed, throttle, CSRF, CSP, audit log, recommendation of additional web server authentication, CLI as the preferred way.
- **Two writers into one archive.** A tab that was reloaded, two browsers, a cron trigger in phase 5. Mitigation: the per-tick lock on the run (3.4), the active/interrupted rule, and tests that tick in parallel.
- **Hosting limits.** The same as in phase 3: per-request time, `memory_limit`, a web server cutting long responses (the download), `disable_functions`. Mitigation: short ticks, resumable everything, the download warning and the server-access advice; spikes 1a and 1b on the live host's kind of setup.
- **Refactoring the CLI commands** (work packages 3, 4, 5) can change behaviour. Mitigation: the existing tests stay as they are and must pass after each step; services return data and do not print.
- **Download of multi-gigabyte files through PHP** is slow and fragile by nature; the interface says so and offers the server access path. It is a convenience (CONCEPT 5.4).
- **Session and token storage in files** is simple and works everywhere; it is not meant for hundreds of users. One administrator is the design.
- **Scope creep** towards phase 5 (schedule and retention fields, "next run"): the pages leave those places out until phase 5 adds them.

**Decisions** (1-4 settled with the owner on 2026-10-21; 5-12 were proposals, confirmed as proposed on the same day)

1. **Scope – settled (2026-10-21):** only phase 4 in this plan; schedule, trigger, retention and encryption are phase 5 with its own plan.
2. **Technique – settled (2026-10-21):** server-rendered HTML, one CSS and one JS file, no build chain, no framework.
3. **Access – settled (2026-10-21):** one administrator with a password (Argon2id), own login with throttle and CSRF; the interface can be switched off. Basic authentication of the web server in front is documented as an addition, not required.
4. **Manual backup – settled (2026-10-21):** ticks driven by the browser; no background process started by the interface. (A CLI process or the phase 5 trigger may continue the same run.)
5. **Off by default - settled (2026-10-21):** `web.enabled = false` until `threadsafe admin enable` or the web setup with a key file – see 3.1/3.2.
6. **Where the code lives - settled (2026-10-21):** `public/index.php` as the only entry point and the document root on `public/`; the whole tree under the web root is supported with `.htaccess` protection but is reported by the installation check as the weaker setup.
7. **Download tokens - settled (2026-10-21):** valid for two hours for one file in one session, repeated use allowed for Range, each use audited, instead of CONCEPT's "single-use"; this is a deliberate deviation – single-use cannot be combined with resume.
8. **Language - settled (2026-10-21):** English only in the first version (like the CLI and all repository text), texts kept apart for a later translation.
9. **Restore kit - settled (2026-10-21):** the interface builds `restore.php` itself and generates `restore-key.php` with a random key it does not store; no copy of the secret stays on the instance.
10. **Several users - settled (2026-10-21):** not now; `admin.json` has a user list so roles can be added later without a format change.
11. **Deleting a profile - settled (2026-10-21):** removes only the profile file; its backups stay on disk unless the person ticks "also delete its backups" on the confirmation page.
12. **Dashboard freshness - settled (2026-10-21):** a status is computed from the sidecars and the file system on each page load (cheap), a database test only on request; no background refresh and no cache until a measurement shows a need.

## 8. Findings of work package 1 (spikes)

Scripts: `tools/spikes/web-download.php` (1a), `web-ticks.php` (1b), `web-basics.php` (1c, 1d, 1e), `web-datacheck.html`/`.js` (1f), and a new section in `host-probe.php` (password hashing on the live host). Measured on 2026-10-21 in the Docker stack (PHP 8.4.25, Apache `mod_php` with `prefork` as in the target container, a 400 MB file); the text of the sections above is corrected where a finding changed it.

1. **Download (1a): the planned technique works and needs little memory.** 400 MB streamed in 1 MB blocks with `flush()`: 1.5 s (about 250 MB/s locally; `readfile()` 1.1 s), the SHA-256 of the download equals the file, PHP peak memory 4 MB (`readfile()` 8 MB). Ranges `a-b`, `a-` and `-n` return 206 with the right `Content-Range` and the right bytes; a start beyond the end returns 416. A client that goes away after 2 s is noticed: `connection_aborted()` is true after the next `flush()` **even with `ignore_user_abort(true)`**, and the script stopped after 24 MB, so the check belongs in the loop. **A slow download is not cut by `max_execution_time`:** the web setting is 30 s, a download throttled to 8 MB/s ran 48 s without `set_time_limit(0)` (on Linux the limit counts CPU time, not the wait for the client); `set_time_limit(0)` stays as a safety for hosts where it counts wall time. *Not measured yet: the live host (FastCGI, web server in front, 30 s per request in the earlier probes). Run `web-download.php` there with a file of a few hundred MB and `curl --limit-rate`; if the host cuts the download, the warning of 3.6 is exactly for that.*
2. **Locks across ticks (1b): the engine is safe, but its notion of "interrupted" is wrong for the web.** Two requests ticking one run at the same moment: one tick happens, the other is refused with the engine's message ("being executed by another process"); no tick is lost or done twice. A request killed with `kill -9` in the middle of a tick leaves the run `running` with the state of the last saved tick and the lock released, and the next request carries on from there. **But** between two ticks no lock is held, so `RunStore::isInterrupted` says "interrupted" for a run whose browser is waiting for the next request, and the CLI's global lock `backup.lock` is free as well, so a CLI backup could start next to a running web backup. Corrected in 3.3 and 3.4 (active = lock held or updated recently; `BackupService` applies the rule for both front ends). The overhead of a tick besides the work (load, lock, save) is about 3 ms.
3. **Password hashing (1c):** PHP 8.4 has `argon2id` (also `argon2i` and `2y`); `password_hash(..., PASSWORD_ARGON2ID)` takes 185 ms, verify 156 ms (default cost m=64 MB, t=4, p=1; bcrypt at cost 12: 153 ms); it works under `memory_limit=16M` (the library allocates outside PHP's memory manager). The live host is not known yet: the new section of `tools/spikes/host-probe.php` prints `password_algos()` and the timing.
4. **Building `restore.php` on request (1d):** 210 KB from 869 KB of code in 227 files takes 1.4 s the first time and 1.0 s the second, peak memory 5.6 MB. Fast enough to do inside the request; a host several times slower is still far inside 30 s.
5. **Resumable SHA-256 (1e):** `serialize()` of a `HashContext` works in PHP 8.4; with base64 it is a 447 byte string that fits the JSON state. A 512 MB file hashed in 9 ticks of 64 MB, saving and restoring the context in between, gives the same SHA-256 as `hash_file` at the same speed (about 1.5 GB/s here). So the hash is not what makes a verify slow; the inflate and CRC of the entries are (phase 3, finding 4: about 16 GB/min on this machine).
6. **Is `data/` reachable? (1f):** the browser can answer it. A script on the page fetched three probe URLs and got `200` plus the content (open directory: EXPOSED), `403` (`Require all denied` in `.htaccess`) and `404` (missing). It needs `connect-src 'self'` in the CSP: **the draft CSP of 3.2 lacked it, which would also have blocked the tick requests** (the restore wizard has it). The probe only proves what is reachable at the URL where `data/` would be mapped, and a 404 may also mean that the probe file does not exist, so the page writes the file first (3.9).
