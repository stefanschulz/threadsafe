# Phase 13 – the connector: a site that cannot run ThreadSafe is backed up, planned and kept by a ThreadSafe elsewhere

**Status:** **planned, not built; the version is stable (1.0.0, 2026-11-05) and the owner asked on 2026-11-09 for the plan of the first satellite, the WordPress one: section 9 is that plan** (written down 2026-11-03 at the owner's request after a discussion; the decisions of section 7.2 were **gone through with the owner on 2026-11-09 and all follow the recommendations**, see 7.1; the field test of `threadsafe-backup.php` that decision 11 waited for is done, [PHASE12.md](PHASE12.md) section 8).
**Context:** [PHASE12.md](PHASE12.md) is `threadsafe-backup.php`, the one-off backup of a site without ThreadSafe (its wizard, its shell mode, its closed directories); [CONCEPT.md](CONCEPT.md) section 9 "A remote source" is the older idea of a profile that reads its site over SFTP, which this plan replaces with a better one for the case below; [SCHEDULE.md](SCHEDULE.md) is the trigger and the schedule that stay as they are; [BACKUP.md](BACKUP.md) section 11 describes the tool; [WORDPRESS.md](WORDPRESS.md) and [JOOMLA.md](JOOMLA.md) the website types.

## 1. Goal and scope

**The case.** A WordPress site on a host where nothing but the site itself can be installed (no second website, so no ThreadSafe), with no cron and probably no shell. PHP 8.4 runs (a `cgi-fcgi` build; the limits of a request, say 30 s, are read at run time). The owner has a ThreadSafe with cron elsewhere and wants **planning, retention and the catalog there**, and the backups to arrive there without a person clicking through the wizard of `threadsafe-backup.php` every time.

**What exists today.** `threadsafe-backup.php` makes an encrypted backup of the site it lies in, in steps that fit a request, and offers a download per part with resume ([BACKUP.md](BACKUP.md) section 11). It has no schedule, no retention, no list of sites, and **nothing that a program can drive**: its only door is the wizard in a browser, with a login by key file and a session. The engine, the encryption (the host needs only the public key), the throttle and the download (`Web\Download`, `Web\ByteRange`) are there.

**What is missing:**

1. **A door for a program**: start a backup, run its steps, list the parts, fetch them, tell the host that a part has arrived. Signed, throttled, off when switched off.
2. **The other side**: a profile that is a *remote site*: the schedule of ThreadSafe starts the backup there, runs it step by step over HTTPS, pulls the parts, checks them and files them in its own storage as an ordinary backup (so that listing, checking, retention and the restore wizard work unchanged).
3. **A way to install and switch it for people who work in the CMS**: a thin **plugin** (WordPress first, Joomla if it is wanted) that brings the tool, shows the pairing string and has the off switch, and lets the administrator choose the directory of the archives.

| In scope | Out of scope (later, or never) |
|---|---|
| the **agent** mode of `threadsafe-backup.php`: a signed API with `status`, `start`, `tick`, `list`, `part`, `done`, `abort` | **SFTP / FTP** in either direction (PHP has no SFTP built in; the pull is HTTPS with `Range`; an SFTP copy by hand stays possible, the files are ordinary) |
| a **remote profile** (`remote` block) and its run in ticks: start, steps, pull with resume, SHA-256 check, sidecar, the word to the host | a **restore** onto the remote host (the restore wizard of `threadsafe-restore.php` is for that, unchanged) |
| the **backup directory** as a setting of the host side (plugin form, wizard, shell), also outside the web root | a push from the host to the central ThreadSafe (the central side asks, the host never calls out) |
| the **WordPress plugin** as the packaging (install, pairing, switch, directory); the Joomla one as an option | WP-Cron as the scheduler (it runs on page views only) |
| tests on the Docker stack behind a real Apache with limits (all three database servers), a field test on the owner's host | a hosted service, several users, roles |

## 3. Design

### 3.1 The agent API

One address on the host, `threadsafe-backup.php?api=<action>` (or the same path of the plugin's copy of the tool). It answers JSON, never HTML, and only when the agent is **switched on** (the switch is a flag in the host's configuration; the plugin's activate and deactivate set it; off, the answer is the same 404-like page a stranger gets today).

| Action | Method | What it does |
|---|---|---|
| `status` | GET | version, PHP and its limits (`max_execution_time`, `memory_limit`), the type and the version of the site, free space, the state of the last run, the time of the host (for the clock check). Used by `profile test`. |
| `start` | POST | starts a run with the profile of the host (3.4), the one-at-a-time rule and the space check of the app. Returns the run id. |
| `tick` | POST | one step of at most the budget of the host (20 s); returns the progress (the same words the wizard shows) and whether the run is finished. |
| `list` | GET | the backups on the host: name, parts with size and SHA-256, the sidecar file, status. |
| `part` | GET | one part or the sidecar, with `Range` / `If-Range` and the SHA-256 as `ETag` (`Web\Download`, unchanged). |
| `done` | POST | the central side confirms that it holds a backup whole (it names the SHA-256 of every part); the host may delete older ones by its rule `keepOnHost`. |
| `abort` | POST | gives up the run and cleans up, as the wizard's "give up". |

**Signed requests, no password and no `Authorization` header.** Every request carries `X-ThreadSafe-Time`, `X-ThreadSafe-Nonce` and `X-ThreadSafe-Signature` = HMAC-SHA256 (a 256-bit secret shared at pairing) over method, path with query, time, nonce and the SHA-256 of the body. The host accepts a time within ±120 s, remembers the nonces of that window (a small locked file) and refuses a repeat. A wrong signature counts in `Throttle::begin()` as a wrong key does today (and, per the open finding 2 of the review, the global count is accepted for backups: they are not time-critical). Why not the REST API of WordPress with application passwords: it loads the whole of WordPress (all plugins, the cache plugin, the firewall plugin) for every step of 20 s, and on `cgi-fcgi` a host often does not pass the `Authorization` header to PHP at all. Custom headers usually pass; if a host strips them too, the same three values may travel as query parameters (decision 5, spike 1).

**What the API does not do: it does not configure** (decision 2). It cannot change the recipients of the encryption, the directory of the archives, the exclusions or the database access; these are set on the host by a person with the rights of the CMS (3.4). A leaked secret then lets an attacker start backups and read encrypted archives they cannot open; it does not let them add their own key to later backups.

### 3.2 Pairing and the keys

1. On the host (plugin page, wizard, or `php threadsafe-backup.php agent --pair` in a shell) the agent makes the secret and shows the **pairing string** once: `ts1:` and base64url of `{url, secret, profile-id, fingerprint}`; the secret is stored in the host's configuration (mode 0600, a file in the workspace with the random name of `BackupWorkspace`).
2. On the central ThreadSafe the person makes the profile (`--pairing-file` or the field in the form), and makes a **key pair** there (`keys new`): the **secret key stays on the central side**, the public key is pasted into the plugin page (or `--recipient` in a shell). Nothing on the host can decrypt a backup, also not an old one.
3. `profile test` calls `status` (signed) and shows the PHP limits, the type and the clock difference.

The `profile-id` of the pairing is the id the central profile has: the host makes its backups under that name (`BackupTarget::profile()` takes it instead of `site`), so that the pulled files, whose names and sidecar carry the profile id, are ordinary members of the central profile's storage (open point 3, spike 2).

### 3.3 The remote profile and its run

A profile with a `remote` block has no local site; its `backup` is `RemoteBackupRun`, a task like every other, started by the existing schedule, the trigger and `backup <profile>`:

1. **start**: `status`, then `start` (a run already going on the host is taken up, not doubled); the run id goes into the state.
2. **tick**: `tick` in a loop, each call within the budget of the central tick; a failed request is retried with a pause, the run on the host keeps its state and continues (its records are the app's).
3. **list**: the parts and their SHA-256 from `list`.
4. **pull**: every part with `Range` from the byte that the local `.part` file has (as the browser resumes today), checked against the SHA-256; the sidecar file the same way. The files appear in the storage of the profile **only when whole and checked** (written to the work directory first, as the encrypted parts are today).
5. **done**: `done` with the SHA-256 list; the host keeps `keepOnHost` backups (default 1: so that a transfer that failed in the night can be fetched again) and deletes older ones.

The sidecar is **fetched, not made**: the sidecar of an encrypted backup is minimal and cannot be made again from the archive ([ENCRYPTION.md](ENCRYPTION.md) section 2), and the catalog lists by sidecar. Retention, the pins, the checks and the restore work on the pulled backup as on any other. A failed run is visible like any failed backup (the dashboard, the heartbeat).

### 3.4 The directory of the archives (and of the state)

A setting of the host side, with a default that survives updates:

- **Where:** the field in the plugin ("Directory for backups"), the options page of the wizard (exists), `--storage` and a new `--workspace` in the shell. It may lie **outside the web root** (the parent of the document root is often allowed on a shared host); the checks are the ones that exist (`SitePath`, `open_basedir`, symlinks, writable, free space: `BackupTarget`, `BackupWizard`), and the test of reach is needed only for a directory inside the web root.
- **Default:** `wp-content/uploads/threadsafe-<random>/` for WordPress (inside the web root: closed by `.htaccess` and tested by the probe), **never inside the plugin directory**: WordPress replaces the whole directory of a plugin when it updates or uninstalls it, which would delete the backups and the pairing. For the same reason the **state of the tool** (profile, run records, the pairing secret) lives in the workspace there, not next to the file of the tool; today the tool unpacks itself into `.threadsafe-backup/` next to itself, so a **setting for the place of the workspace** is a change of the tool (work package 2).
- **Who may set it:** only a person with `manage_options` (WordPress) or the corresponding right; the path is checked like every path of the tool: no stream wrapper (`phar://`, `php://`), no program directory, no directory of another site.
- **Changing it later:** archives that exist stay where they are; the plugin says so and offers to move them or to leave them. The agent knows one directory at a time, so `list` shows what the current one holds; the central profile pulls and then asks the host to forget what it has (`done`).

### 3.5 The plugin (WordPress) and its sibling (Joomla)

A packaging, nothing more: it **places the tool** (and, in agent mode, no key file: the pairing replaces it), **shows the state and the pairing string**, **switches the agent on and off** (activate/deactivate), and **sets the directory** and the **public keys**. It does not carry logic of the backup, loads nothing of WordPress for a tick (the agent is the tool's own entry, which reads the database access from `wp-config.php` through the existing WordPress type), and checks `Requires PHP: 8.4` before it does anything else. The settings page also shows the result of the reach probe of the directory, the free space, the time of the last backup and the clock difference. Uninstall removes the workspace; the archives only if the box is ticked.

**Joomla** (Joomla 5 and 6, which ThreadSafe already supports) needs the same thing: a system plugin for the install, the switch (enable/disable in the plugin manager) and the settings (the pairing string as a read-only parameter, the directory and the keys as fields), with `php_minimum` in the manifest; a page of its own would need a small administrator component and can wait. The agent is the same; only the wrapper differs. PrestaShop modules would be possible and are not wanted for now.

**Distribution:** a ZIP in the GitHub release, uploaded in the CMS. The directory of wordpress.org will probably not take the self-unpacking single file (a payload archive inside code is hard to review); a build with the plain source files would be needed for it, and is not planned. Joomla's JED is the same.

### 3.6 Security, in short

- **A resident door on a production site** is new: the one-off tool takes itself off after the backup. Mitigations: the switch (off by default until paired; off when the plugin is deactivated), HTTPS only (the agent refuses a plain-http request unless the owner ticks it, as the login does), a 256-bit secret, signed and timed requests, the throttle, an optional **IP allowlist** in the host's configuration (the address of the central server), and no action that configures.
- **A firewall plugin** (NinjaFirewall on the owner's host) may block a regular signed request with a long path: to be tried on the real host (spike 3); the answer may be a rule for the address of the agent.
- **The database password** lies in the workspace as in `wp-config.php` (the tool reads it from there, or the profile holds it, mode 0600).
- **The review of this session applies:** the three single-file tools got the throttle that counts before it compares, the closed directories with a reach probe, no message before the key, and the security headers; the agent reuses them and adds the signature.

## 6. Risks and open points

- A host or a firewall that blocks or rewrites the regular signed requests (spike 3): the fallback is the query string, and in the worst case no agent on that host; the manual wizard remains.
- The **number of requests**: a backup of a few hundred MB is some dozens of 20-second steps and as many requests for the parts; a host with a low limit of simultaneous or per-minute requests may refuse some. The central side retries with a pause.
- A pulled backup in the catalog (open point 3, spike 2): the profile id in the name and in the sidecar must agree with the central profile.
- **The clock:** a difference of more than the window makes every request fail; `status` reports the host's time, and `profile test` says so in words.
- **Plugin updates** replace the plugin directory: everything that must survive lies in the workspace (3.4), and a test proves it.
- The tool needs **PHP 8.4**: an older PHP on the host cannot run any of it; the plugin says so instead of failing.
- A resident agent is a **permanent target** (3.6): it is the price of the planning from outside; a person who wants no resident door uses the wizard by hand, as today.

### 7.2 The decisions and their recommendations (settled, see 7.1)

1. **Signed requests of our own, or the REST API of WordPress?** *Recommended: signed requests of our own* (3.1): CMS-neutral, no WordPress load per step, no `Authorization` header.
2. **May the API configure?** *Recommended: no* (3.1): the recipients, the directory, the exclusions and the database access are set on the host only. The price: the pairing needs a visit to the plugin page once.
3. **The pulled backup's profile id** (3.2): the pairing carries the central profile's id and the host makes its backups under it. *Recommended*, to be confirmed by spike 2.
4. **Resident or one-shot?** *Recommended: resident, switched off by default and off when the plugin is deactivated*, with an optional IP allowlist; the one-off tool with its self-removal stays as it is.
5. **A fallback of the headers into the query string** if spike 1 shows that the host strips them. *Recommended: yes, only then.*
6. **`keepOnHost`, default 1** (3.3): the host keeps the newest backup after a verified pull, so that a failed transfer can be repeated. *Recommended.*
7. **The directory default** `wp-content/uploads/threadsafe-<random>/`, never in the plugin directory (3.4). *Recommended.*
8. **WordPress first, Joomla only on demand** (3.5). *Recommended.*
9. **Distribution as a ZIP in the GitHub release, not in a directory** of the CMS (3.5). *Recommended.*
10. **No SFTP and no WP-Cron** (section 1). *Recommended*; the owner's SFTP copy by hand stays possible.
11. **Do it at all, and when?** The field test of `threadsafe-backup.php` on the owner's host (phase 12, work package 10) comes first: it shows whether PHP, the limits, the firewall and the transfer are what this plan assumes. *Recommended: after that test.* **Met** (2026-11-05, phase 12 is field-tested with PrestaShop, Joomla and WordPress sites); but the owner's WordPress host is the one that cannot run ThreadSafe, so M0 and M4 test it for the agent.
12. **The pointer file in `wp-content`** (9.2, 4) that lets the entry find the workspace without loading WordPress. *Recommended.* The alternative, a fixed directory name, would make the workspace guessable.
13. **A pre-release first** (9.4): `1.1.0-rc.N` for the field tests, `1.1.0` after them. *Recommended*: the agent is a resident door; a release candidate is cheap.
14. **Field test A before the plugin** (9.3): M4 (the tool by hand on the owner's host) before M5 (the plugin). *Recommended.*
15. **A second mode of a remote profile: leave the backups on the host** (asked by the owner on 2026-11-09). A profile setting `transfer: pull | keep`, `pull` the default (3.3). In `keep` the central ThreadSafe starts the backup by its schedule and **watches** it (done or failed, size, time: the dashboard and the heartbeat), pulls nothing and makes **no entry in the catalog**; the retention is a **rule on the host** (the newest N, not older than X days; set there only, by decision 2: the central side never deletes on the host). Costs and limits to say in the interface: the backup lies on the same server as the site (a warning, because that is what a backup elsewhere is for), the central side cannot read or check it (it compares the size and the SHA-256 that the host names), and a restore takes the parts from the host first (the wizard of the tool offers them for download). `keepOnHost` greater than 1 with `pull` already keeps several on the host. *Recommended: yes, but not in the first cut (`1.1.0-rc.1`): a small package after it (`1.1.x`)*; the API needs nothing new for it (`list` has all it needs), the cost is a second set of cases in the tests.

## 8. Findings of the spikes

**By reading the code, 2026-11-09** (no spike has been run on the real host yet):

- **Spike 2 (the pulled backup in the catalog):** `BackupCatalog` and `LocalStorage::names()` attribute a file to a profile by the profile id in its **name**, and the name of an encrypted backup cannot change; so the host makes its backups under the central profile's id (3.2) and nothing in the catalog has to change. To be proven in M2 with a real pulled backup.
- **The stub blocks an agent without a key file** and **the workspace shares the directory of the program**: see 9.2, 1 and 2. Both are changes to the tool, not to the plan's idea.

**M0: the probe on the owner's WordPress host (2026-11-09).** `tools/spikes/agent-probe.php` was uploaded to `wp-content/plugins/` and to `wp-content/uploads/` of the host and run from the owner's Windows machine (a PHP without a bundle of certificate authorities: the probe now finds one or takes `--cainfo`, which is how the first attempt failed). The host: PHP 8.4.27 as `cgi-fcgi`, Apache 2.4.69, `sodium` and `zlib` present, `max_execution_time` 240, `memory_limit` 512M, `post_max_size` 128M, no `open_basedir`, WordPress in a sub-directory of the document root. **Both places gave the same answers and none was a problem:**

- **The headers arrive.** `X-ThreadSafe-Time`, `-Nonce` and `-Signature` reach PHP unchanged, and so do the same values in the query string. **Decision 5 stands: the fallback is not needed and is not built.** An `Authorization` header arrives on this host too (the REST API of WordPress would have worked here; decision 1 stands: other hosts strip it, and WordPress is not loaded per step).
- **A POST of 200 KB with a query of 1500 characters arrives whole** (SHA-256 equal), and **a client called `ThreadSafe-Agent` is treated like any other**: nothing on the host (NinjaFirewall included) objects to the shape of a signed request.
- **Range works**: 206 with the right `Content-Range` and the right bytes from the middle of a 20 MB file, a stale `If-Range` gives the whole file, the answer is not compressed behind our back; 20 MB in 0.8 s to the owner's machine. A cut transfer can go on.
- **Requests of 10, 20, 30 and 40 s ran through** (the test stops at 40 s; the PHP limit is 240 s). The step budget of the agent (at most 20 s, read from `max_execution_time` at run time) has room.
- **The clocks differ by 0.2 s**; the window of 120 s is generous.
- **PHP runs in `wp-content/uploads` too** on this host. The plan does not need it (the entry stays in the plugin directory, 9.2, 3), but it means that decision 7 (the workspace in `uploads/threadsafe-<random>/`) has no obstacle here. **Decision 7 stands.**
- **`disk_free_space` reports the volume (6.7 TB), not the quota of the account.** A shared host has a quota far below that, and PHP cannot see it. The space check of the agent (`start`, `status`) cannot trust the figure: see 9.6.
- **Not tested:** the headers and the limits from the machine of the central ThreadSafe (the probe ran from the owner's Windows machine: the route and the clock can differ; M4 and the `status` action show it), the number of simultaneous requests, requests longer than 40 s, and a directory outside the document root (M1 tests whether PHP may write above `htdocs`).

## 9. The plan for the first step: the WordPress satellite (2026-11-09)

### 9.1 What the owner gets, and when it is done

The owner's WordPress site on the host that can run nothing but itself (no second website, no cron, PHP 8.4 as `cgi-fcgi`) is **backed up by the schedule of the ThreadSafe on the owner's own server**, the encrypted backups arrive there by themselves, and retention, the catalog, the checks and the restore wizard treat them like any other backup. On the WordPress side it is **one plugin** (`threadsafe-connector`): upload the ZIP, activate, paste the public key, copy the pairing string into the central ThreadSafe. **Done** when the owner's site has been backed up by the schedule for a week without a person, and one of those backups has been restored with `threadsafe-restore.php` on another domain.

The scope is sections 1 to 3 as written, WordPress only; the Joomla wrapper stays work package 8 of section 5.

### 9.2 What reading the code showed (changes to sections 3.4 and 3.5)

1. **The stub refuses the web without a key file.** `Build\ToolStub` (`{KEY}`) answers 403 "No access key yet" before anything else runs when `threadsafe-backup-key.php` is missing. The agent has no key file (the pairing replaces it), so the stub of the **backup tool** needs a parameter that lets an `?api=` request through to the entry (the stub stays one class; the restore tool and the installer are byte-identical as before, a test keeps that). **Built in M1.2, and narrower than first written:** the request passes the stub without a key file only if the tool was **set up for an agent** (the constant `THREADSAFE_WORKSPACE` is defined, or a `data-*/agent.json` lies in the tool's directory); a stranger who adds `?api=` to a tool that was never set up gets the same page as before and nothing is written, which keeps the property that the stub writes nothing until a person has put a key file next to it. The agent then checks the switch and the signature itself and answers like a stranger (the 403 page, no hint) if it is off, unpaired or wrong.
2. **The program and the workspace share a directory today.** The stub unpacks the program into `.threadsafe-backup/` next to the tool, and `Web\BackupWorkspace` puts `data-<random>/` (profile, run records, throttle file, in the plan also the pairing secret) and `storage-<random>/` (the archives) into the same directory. A plugin update **replaces the whole plugin directory**: the program would unpack again (harmless, once), but the pairing, the records and every archive would be gone. So the **workspace moves out of the plugin directory** and the program stays: `BackupWorkspace::in()` takes a directory from the settings, the stub's own unpack directory is left where it is.
3. **The entry file stays in the plugin directory, the workspace goes elsewhere.** The agent must be a PHP file that the web server executes: many hosts and security plugins forbid PHP in `wp-content/uploads` (and NinjaFirewall on the owner's host may). The plugin directory is meant to hold PHP. The workspace (no PHP in it) goes to `wp-content/uploads/threadsafe-<random>/`, or outside the web root if the host allows it (3.4).
4. **A pointer file finds the workspace without loading WordPress.** The entry cannot read a WordPress option (loading WordPress per step is what this design avoids). The plugin writes `wp-content/threadsafe-agent.php` (`<?php return ['workspace' => '/absolute/path'];`, mode 0600, closed by `.htaccess`) when the directory is set; the file lies **in `wp-content`, which a plugin update does not touch**. It is read by the **plugin's own entry file** (a few lines that run before the tool and then load it): that file defines the constant `THREADSAFE_WORKSPACE` with the path, and the tool takes its workspace from the constant (`BackupEntry::workspace()`, built in M1.2; a shell has `--workspace` instead, M1.4). The tool checks the path as it checks every path (`BackupWorkspace::customProblem()`: absolute, no `..`, no stream wrapper, neither inside the directory of the tool nor around it) and answers "set up wrongly" with a line in the error log if it is not good; it never guesses. A workspace inside the site is left out of the archive by `BackupTarget::selfExcludes()`. Without the constant the tool works as today (the one-off wizard, the workspace next to it). **For M5:** the pointer file and the plugin's entry file are the plugin's own and must be left out of the archive too (a restored copy must not carry a pointer to the workspace of another site).
5. **The catalog goes by the profile id in the file name** (`BackupCatalog::find()`, `LocalStorage::names()`), and the file of an encrypted backup cannot be renamed. So the host must make the backup under the central profile's id: the pairing string carries it (3.2), `BackupTarget::profile()` takes it instead of `site`. Spike 2 is thereby answered by reading; milestone M2 proves it with a pulled backup.
6. **An API version.** `status` names an integer version of the API, the pairing string carries the one it was made for; the central side refuses a host of another major version with a sentence that says which side to update. The plugin and the central ThreadSafe are updated separately (ZIP upload in WordPress; an `Update URI` header with the update from the GitHub release is possible later and not planned).

### 9.4 The release path

The agent is a **resident door** on a production site (3.6), so the code of M1 to M5 goes out first as a **pre-release** (`1.1.0-rc.1`: the workflow marks a version with a suffix as a pre-release, and the update from the System page orders it above 1.0.0), is field-tested in M4 and M6, and becomes **1.1.0** with M7. The agent is **off in every installation that has not paired it**, so 1.1.0 changes nothing for the people who do not use it.

### 9.5 Tests that are new in this step (on top of section 4)

- **The stub:** a request with `?api=` passes without a key file, any other web request still gets the 403; the stubs of the restore tool and the installer are byte-identical to before.
- **The workspace:** the pointer file is read (a missing, damaged or world-readable one is refused), the plugin directory replaced as an update does leaves the archives, the pairing and the throttle file where they are, the workspace inside the plugin directory is refused.
- **The plugin on an old PHP:** a PHP below 8.4 simulated (activation refused with the message, no fatal error in the admin).
- **The API against the owner's firewall:** the probe of M0 stays as `tools/spikes/agent-probe.php` and its result in section 8.

### 9.6 Risks of this step, besides section 6

- **NinjaFirewall or the host strips the headers or blocks the signed request** (M0 finds out early): the fallback is the query string (decision 5); in the worst case there is no agent on that host and the manual wizard remains.
- **The free space cannot be known** (M0: `disk_free_space` shows the whole volume, 6.7 TB, not the quota of the account). The space check of the app (`SpaceCheck`, the size of the site against the free space) stays, because it catches the small cases, but the agent must treat **a full disk as a normal failure**: a write that fails ends the run with a sentence ("the disk or the quota of this host is full: free some space or keep fewer backups on the host"), removes what the run left (parts and work directory, as "give up" does) and leaves the older backups alone. M3 tests it with a small file system as the workspace; the plugin page tells the person that the figure for free space is the volume's.
- **The time of one request on the host** (30 s on the owner's other host): the step budget of the agent is read from `max_execution_time` at run time, as the wizard does; M0 measures it.
- **A plugin that holds a secret** is a target for anyone who can read the files of the site: the secret lies in the workspace (0600, closed directory) and, by decision 2, cannot reconfigure anything; a person who can read it can start backups and fetch encrypted archives, not decrypt them.
- **Two ThreadSafe versions** (the host's plugin and the central one) drift apart: the API version of 9.2, 6 and a line in the System page of the central side ("the satellite of profile X is of version Y").

### 9.7 As built: M1, the agent in the tool (2026-11-09)

Four commits: **M1.1** the signature, the replay store, the pairing string and the settings; **M1.2** the stub gate and the workspace elsewhere; **M1.3** the API; **M1.4** the setup (page "The agent" of the wizard and the shell command). `composer check` 4041 tests green; a smoke test of the built tool (set up with the shell command, then a backup made, listed and fetched through the API behind PHP's built-in web server) ran stub, entry and agent together. **What differs from the plan above, and what M2 must know:**

- **The classes** (all in the backup tool only, `RestoreBuilder::ONLY_BACKUP`): `Web\Agent` (the API), `Web\AgentSignature` (signs and checks), `Web\AgentReplayStore` (the nonces, a locked file), `Web\AgentPairing` (the string `ts1:`, its fingerprint), `Web\AgentConfig` (`agent.json` in the data directory of the workspace), `Web\AgentSetup` (profile copy, pairing, sync, unpair: the one set of rules for the page, the shell and the later plugin), `Web\AgentPage` (the HTML), `Cli\ToolAgentCommand`, `Cli\ToolProfileOptions` (the options of the profile, moved out of `ToolBackupCommand` and shared). `Web\Request` carries `uri` and the raw `body` (not for a multipart form, at most 1 MB): what a signature covers.
- **The signature is checked before the time** (`AgentSignature::verify()`): only a sender that holds the secret is told that its clock is wrong (`403 {"error":"clock","hostTime":...}`) or that a request was seen before (`403 {"error":"replay"}`); a stranger gets the plain "Not found." for every reason: a tool never set up (nothing is made for it), an agent that is off or unpaired, plain http, an address not on the list, a request held back by the throttle, no or a wrong signature (counted and logged in `agent.log` like a wrong key). The central side therefore sees 404 for anything it cannot be told: `profile test` must say "the agent does not answer: off, not paired, the address not allowed, a wrong secret or http" and not guess.
- **What the central client must send (M2):** `X-ThreadSafe-Time`, `-Nonce`, `-Signature` over `"TS1" LF METHOD LF path-and-query LF time LF nonce LF sha256(body)` (`AgentSignature::headers()` makes them; the central side uses the same class), the path and query **exactly as sent** (what the host sees in `REQUEST_URI`), the body as sent; `tick`, `abort` take `run=` in the query, `part` takes `backup=` and `file=`, `done` a JSON body `{"backup": "<name>", "parts": {"<file>": "<sha256>", ...}}`. A tick answers `running`, `busy` (another process works on the run: ask again), `failed` (with `error`) or `finished` (with `backup`), always with `progress` and `percent`. The sidecar is fetched like a part (`file=<backup>.json`).
- **`done` keeps the newest `keepOnHost` complete backups** and removes the rest, **but never a backup that is newer than the one just held** (it has not been fetched yet); with `keepOnHost` 1 and a newer unfetched backup, the held one goes. A backup that a run is working on stays. Every part of the backup must be named with its SHA-256 or nothing is deleted (409).
- **The stub gate** is narrower than first written (9.2, 1): `?api=` passes without a key file only on a tool that was set up for an agent. **The workspace elsewhere** is the constant `THREADSAFE_WORKSPACE` (`BackupEntry::workspace()`, `BackupWorkspace::customProblem()`), and `--workspace` in the shell; a workspace inside the site is left out of the archive.
- **The agent makes encrypted backups only** (`AgentSetup::problem()`): a profile without a public key cannot be paired, in the page and in the shell; there is no passphrase mode (the host would have to keep it) and no plain mode. The profile of the agent is a copy of the profile `site` of the tool (the wizard's first pages or the shell options) under the id of the central profile; `agent-sync` copies it again after a change. Nothing in the API configures.
- **The page "The agent"** is reached from the summary page; it shows the pairing string once (afterwards only the fingerprint), switches on and off, sets the list of addresses (IPv4 and IPv6 ranges), `keepOnHost` and plain http. A host without a shell has nothing else; the plugin (M5) will do the same through `AgentSetup`.
- **Not done in M1 and left for later milestones:** the connection of the agent's `status` to the plugin page (M5), the proof behind a real Apache with limits and a full disk (M3), the number of requests in a run on a slow host (M4), `transfer: keep` (decision 15).

### 9.8 As built: M2, the central side (2026-11-09)

Four commits (M2.1 to M2.4); `composer check` 4138 tests green; a smoke test of the real command line (`profile add --pairing-file`, `profile test`, `backup shop`, `backups shop`, `verify shop`) against the built tool behind PHP's built-in web server made a backup on the site, fetched it, listed it as an encrypted backup of the profile and checked it. **What differs from the plan, and what M3 and M4 must know:**

- **The profile** (`Profile\RemoteSettings`, the block `remote`: `url`, `secret`, `plainHttp`) has no path (the empty text), no database of its own and the type `remote` (or the one the person gives); it stands on its own, without the classes of the agent, because the profile is part of the restore tool. The secret is stored like a database password (file mode 0600) and masked in everything that is shown. **Plain http needs a consent** (`plainHttp: true`; `--plain-http`, a checkbox in the form). A remote profile has a schedule and a retention like any other; the encryption, the filters, the database, the part size and the compression are set **on the site** and refused here with that sentence.
- **`Remote\AgentClient`** signs every call (`AgentSignature`), reads the answers the way `Web\Agent` writes them, and `fetch()` brings a part into a file: resumes from the byte that is there (`Range` with `If-Range` on the listed SHA-256), checks size and SHA-256, deletes what is wrong, and can be **stopped by the receiver** (`$shouldStop`, asked after every piece) so that a tick with a time limit ends in the middle of a part and the next tick goes on. `CurlTransport` (certificate checked, no redirect, no compression, a stalled transfer is cut, a large one is not) and `StreamTransport` (no curl) were both proved over real HTTP, including a part cut in half and resumed.
- **The run is a phase of the backup run** (`BackupState::REMOTE`, `Remote\RemoteBackupRun`, started by `BackupRun` when the profile is remote), so that the schedule, the trigger, `backup <profile>`, the web interface, retention, the catalog and `verify` need no change: start (the agent's state and its API version; **a backup that an earlier transfer left on the site and that is younger than a day is taken up instead of making a new one**, which is what `keepOnHost` is for), run (a step of the backup on the site per call), list, pull, store (the parts first, the sidecar file last), done, finish. A failure that may pass is tried again after a pause that doubles (at most 6 in a row); one that will not pass ends the run with a sentence that says what to do (the agent says nothing: off, not paired, the address not allowed or the secret changed; the clocks differ, with the time of the site; the API of another version; the profile id differs from the one of the pairing; the backup on the site failed with its reason). A tick with a time limit does not sleep: it says that it waits and the next tick looks again; a run in one process (`complete`) sleeps. A file name that the site names is not trusted: only names of this backup are accepted.
- **`profile test` of a remote profile** (`Remote\RemoteConnectionTest`) asks `status` and reports: address and fingerprint of the secret, plain http, the agent's tool and PHP, the API version, whether the profile is ready under the id, the **clock** (a warning above 60 s, a failure above 100 s), the limits and the free space of the site's volume (with the note that the quota may be smaller), the backups and the run on the site, and the storage and PHP of this machine.
- **The web form** (`Admin\RemoteProfileController`, `/new-remote-profile`, `/remote-profiles`; the edit form of a remote profile is the same): pairing string (not shown again; the page shows the fingerprint), plain http, name, note, storage, schedule, retention. **The `Keys` page and the local filters are not offered** for a remote profile. `ProfileForm::retention()` and `automationSummary()` are shared with the form of a local profile.
- **Not done in M2:** the proof behind a real Apache with 5 s / 64 MB on all three database servers, the cut transfer there, a full disk on the site (M3); the plugin (M5); `transfer: keep` (decision 15); a restore wizard that fetches from the site (the person fetches the parts, as with any backup).

### 9.9 As built: M3, the proof on the stack (2026-11-09)

`tests/Integration/AgentStackTest.php` (group `agent`, ten tests that use what the one before left, about 230 assertions, 1:50 minutes) is **phase 4f of `tests/stack/run.sh`**, after the backup tool (4e). `tests/stack/matrix.sh` is green on MariaDB 10.11, MySQL 8.4 and MariaDB 11.8 (all other phases too); `composer check` is green (4138 tests). **What it does:**

- **The host is the seeded WordPress 7** (service `wordpress7`, mounted writable into the tools container). The built tool and a key file are put into `wp-content/plugins/threadsafe-connector/`, as the plugin of M5 will place them. The test sets the tool up **through the wizard** (key, site, options with the public half of an `age` key pair, the page *The agent*: pairing, then on) and the central side is the tools container: the real command line (`profile add --pairing-file`, `profile test`, `backups`, `verify`, `restore`) and the real classes with curl (`BackupService`, `AgentClient`), with `Support\RecordingTransport` noting every call (action, status, `Range`, seconds) and able to cut a download after some bytes.
